# 사용 설명서

서버를 띄운 뒤 화면에서 무엇을 어떻게 하는지를 순서대로 적은 문서다. 에이전트를 만들고, 미리보기로 시험하고, 발행해서 웹앱이나 API로 쓰고, 로그를 보고, 백업하는 데까지 다룬다. 앞쪽 장은 에이전트 기준이고, 노드를 이어 만드는 워크플로우·챗플로우와 지휘자 에이전트는 '설정' 장 뒤에 따로 모았다. 처음 설치(Python, uv, Node, `.env` 작성, 화면 빌드)는 [설치](ops/install.md)를 먼저 따라 한다. 평소 운영은 [운영](ops/operations.md), 백업과 복구는 [백업과 복구](ops/backup-restore.md), 안전 수칙의 근거는 [보안 확인](ops/security.md)에 있어서 여기서는 되풀이하지 않고 링크만 건다. 화면에 보이는 글자는 작은따옴표로, 서버가 돌려주는 오류 문구는 큰따옴표로 적었다.

기본 흐름은 이렇다. 서버를 띄우고, 에이전트를 만들어 초안을 저장하고, 미리보기로 시험한다. 마음에 들면 발행하고, 발행한 버전을 웹앱이나 API로 쓴다. 한 일은 로그에서 확인한다. 용어는 셋만 짚는다. 런은 메시지 하나를 처리하는 에이전트의 실행 한 번이고, 그 안에서 모델을 한 번 부르는 단위가 스텝이다. 세션은 런이 쌓인 대화 하나다. 워크플로우의 런은 그래프를 한 번 도는 것이라 뜻이 다르고, 그 장에서 따로 설명한다.

## 시작하기

서버는 저장소 루트의 터미널에서 `uv run platform serve`로 띄운다. uv가 PATH에 없는 터미널이면 `python -m uv run platform serve`로 같다. VS Code에서는 `apps/api/app/main.py`를 열어 편집기 위쪽의 실행 버튼(재생 모양)을 누르거나 실행 및 디버그에서 `platform serve`를 고른다. 어느 쪽이든 같은 서버가 뜬다. 콘솔에 JSON 로그가 흐르다가 `server.ready`가 나오면 준비된 것이다.

브라우저에서 http://127.0.0.1:8500 을 연다. 이 주소는 이 PC에서만 열린다. `.env`를 고쳤다면 서버를 다시 띄워야 반영된다.

처음 접속하면 '처음 설정' 화면이 뜬다. '이메일', '비밀번호', '비밀번호 확인'을 넣고 '계정 만들기'를 누른다. 비밀번호는 12자 이상이다. '이름'과 '워크스페이스 이름'은 비워도 된다. 계정은 하나만 만들 수 있고 만든 뒤에는 이 화면이 다시 열리지 않는다. 만들면 바로 로그인되어 에이전트 목록으로 넘어간다.

다음부터는 '로그인' 화면에서 같은 이메일과 비밀번호로 들어간다. 로그인은 1분에 5번까지만 시도할 수 있고, 넘으면 '시도가 너무 많습니다. 30초 뒤에 다시 시도하세요.' 같은 안내가 나온다. 비밀번호를 잊었을 때는 뒤의 설정 절에 있다.

끌 때는 서버를 띄운 터미널에서 Ctrl+C를 누른다. 콘솔 창을 닫아서 끄지 않는다. `uv run`이 앞에 세운 런처가 먼저 끝나면서 정리 중인 서버까지 끝내는 것으로 보여서 정상 종료 기록이 로그에 남지 않는다. 다음에 띄울 때 기동 복구가 뒷정리를 하지만 Ctrl+C로 끄는 쪽이 깔끔하다.

Ctrl+C로 끄면 도는 중이던 런은 '실패'로 끝나고 오류 코드가 `shutdown`으로 남는다. 그때까지 나온 응답과 작업공간의 파일은 그대로다. 승인이나 질문을 기다리던 런은 서버를 다시 띄운 뒤 24시간 안에 답하면 이어서 실행된다. 워크플로우 런도 같은 규칙이다.

Gemini 키 없이 화면부터 둘러보고 싶으면 `.env`의 `GEMINI_API_KEYS`를 비우고 `LLM_FAKE=true`를 넣은 뒤 서버를 띄운다. 모델 대신 정해진 각본이 답하고 실제 모델은 부르지 않는다. 메시지를 보내면 `echo fake-llm`을 실행하는 승인 카드가 뜨고, 메시지가 `질문:`으로 시작하면 질문 카드가, `파일:`로 시작하면 `outputs/결과.txt`를 만드는 응답이 나온다. 워크플로우의 'LLM' 노드는 도구가 없어서 프롬프트 마지막 메시지의 글(200자까지)에 '가짜 응답: '을 붙여 돌려준다. 설정의 'LLM' 화면에 가짜 어댑터로 동작 중이라는 안내가 보인다. 실제로 쓸 때는 `LLM_FAKE`를 지운다.

## 화면 구성

왼쪽 좁은 메뉴에 '에이전트', '워크플로우', '스킬', '로그', '설정'이 있고 맨 아래에 '내 계정'이 있다. 위쪽 띠에는 현재 위치가 나오고, 오른쪽 끝의 둥근 버튼(이름 첫 글자)에서 '내 계정'과 '로그아웃'을 고른다. 왼쪽 위의 W는 에이전트 목록으로 가는 링크다.

- '에이전트': 만든 에이전트가 카드로 나온다. 이름이나 설명으로 찾고, '새 에이전트'로 만들고, 카드를 눌러 빌더를 연다.
- 빌더: 위쪽 탭 일곱 개와 오른쪽 미리보기 패널. 에이전트를 만들고 시험하고 발행하는 곳이다.
- '워크플로우': 노드를 이어 만든 워크플로우와 챗플로우의 목록. 카드를 누르면 캔버스 편집기가 열린다. 뒤의 '워크플로우 만들기' 장부터 설명한다.
- '스킬': 에이전트에 붙일 스킬 패키지(zip)를 올리고 관리한다.
- '로그': 모든 대화와 런의 기록. 워크플로우의 런은 '워크플로우 런' 탭에 있다.
- '설정': 'LLM', '워크스페이스', '작업공간', '사용량', 'HTTP 허용 목록'.
- 웹앱(`/apps/슬러그`): 발행한 에이전트와 대화하는 화면. 왼쪽 메뉴 없이 대화 목록과 채팅만 나온다. 발행한 워크플로우의 웹앱은 `/flows/슬러그`다.

'워크스페이스'와 '작업공간'은 이름이 비슷하지만 다르다. 워크스페이스는 계정이 속한 최상위 단위로 기본값과 보관 기간 같은 설정만 있다. 작업공간은 세션(대화)마다 생기는 폴더로, 에이전트가 파일을 만들고 명령을 돌리는 곳이다.

## 에이전트 만들기

'에이전트' 화면의 '새 에이전트'를 누르면 만들기 창이 뜬다. '이름'만 필수다. '아이콘'은 이모지나 짧은 글자이고 비우면 이름 첫 글자를 쓴다. '슬러그'는 웹앱 주소(`/apps/슬러그`)에 들어가는 영문 소문자·숫자·하이픈 이름(64자까지)이고 비우면 서버가 정한다. '설명'은 목록에 보이는 메모다. '만들기'를 누르면 빌더가 열린다.

에이전트를 지울 때는 카드 오른쪽 위 점 세 개 메뉴의 '에이전트 삭제'를 쓴다. 지운 에이전트의 API 키는 바로 폐기되고 웹앱 주소도 열리지 않으며, 로그에는 '삭제된 에이전트'로 남는다.

빌더 위쪽 탭은 '설정', '도구와 스킬', '파일', '환경변수', '승인과 한도', '발행', 'API'다. 입력에 문제가 있는 탭에는 붉은 점이 찍힌다. 위쪽 띠에는 이 에이전트의 기록만 보는 '에이전트 로그', '저장', 미리보기를 여닫는 버튼이 있다.

고친 내용은 '저장'을 눌러야 초안에 들어간다. 고친 게 남아 있으면 '저장하지 않은 변경'이 표시되고, 이 상태로 다른 화면으로 가려 하면 '이 화면을 떠나면 저장하지 않은 변경이 사라집니다.' 확인 창이 뜬다. 미리보기와 발행은 저장된 초안만 쓴다.

'설정' 탭의 '기본 정보'에서 아이콘, 이름, 슬러그, 설명을 고친다. 슬러그를 바꾸면 웹앱 주소도 바뀐다. '지시문'은 에이전트가 따를 지시를 마크다운으로 쓰는 칸이다. 맡을 일, 말투, 지킬 규칙을 적는다.

'모델과 파라미터'의 '모델'이 '기본 (폴백 순서대로)'이면 설정의 LLM 화면에 나온 순서대로 첫 모델부터 쓰다가 일시 오류(429, 5xx)가 계속되면 다음 모델로 넘어간다. 특정 모델을 고르면 그 모델부터 목록 뒤쪽으로 넘어가고, 목록에 없는 모델은 실패해도 다른 모델로 넘어가지 않는다.

'사고 수준'(reasoning effort)은 모델이 답하기 전에 생각하는 정도다. '최소'부터 '높음'까지 있고 '모델 기본값'이면 모델이 정한다. '최대 출력 토큰'은 기본 16000이고 모델 상한까지 올릴 수 있다. 'temperature'와 'top_p'는 비우면 모델 기본값이다.

'도구와 스킬' 탭의 '도구'는 네 묶음을 스위치로 켜고 끈다. 새 에이전트는 모두 켜져 있다. '셸·파이썬'은 PowerShell 명령, 파이썬 코드 실행, 패키지 설치(`shell`, `run_python`, `install_packages`)다. '파일'은 작업공간 안의 파일 읽기·쓰기·고치기·목록(`read_file`, `write_file`, `edit_file`, `list_files`)이다. 'HTTP'는 허용 목록에 있는 도메인으로 요청을 보낸다(`http_request`). '사용자에게 묻기'는 일하다 확인이 필요하면 질문하고 답을 기다린다(`ask_user`).

필요 없는 묶음은 꺼 두는 편이 안전하다. 스위치 옆의 '실행 전 승인'과 'GET·HEAD 외 요청은 승인' 표시는 지금 승인 모드에서 그 묶음이 승인을 받는다는 뜻이다. 같은 탭 아래의 스킬은 뒤의 스킬 절에서, '하위 에이전트'는 '지휘자 에이전트' 장에서 설명한다.

'파일' 탭은 에이전트가 늘 참고할 자료(규정, 예시 데이터 같은 것)를 올리는 곳이다. '파일 올리기'로 올리면(파일 하나에 100MB까지) 체크된 채로 목록에 들어오고 '초안을 저장해야 이 파일이 들어갑니다.'라는 안내가 뜬다. 체크한 파일은 세션 작업공간의 `agent-files` 폴더에 복사된다. 초안이나 발행 버전이 쓰는 파일은 지울 수 없다. 초안에서 체크를 풀고 저장하면 초안 쪽은 풀리지만, 발행 버전이 쓰는 파일은 그 버전이 남아 있는 동안 지워지지 않는다.

'환경변수' 탭은 에이전트가 실행하는 셸과 파이썬 프로세스에 넣어 주는 값(외부 서비스 토큰 같은 것)이다. '변수 추가'로 '이름'과 '값'을 넣는다. 이름은 영문자·숫자·밑줄만 쓰고 숫자로 시작할 수 없다.

'비밀'을 켠 값은 암호화해 저장하고, 저장한 뒤에는 화면에 다시 보여 주지 않는다. 값 칸에는 '저장된 값 유지 (바꾸려면 입력)'라고 나오고 바꿀 때만 새 값을 넣는다. 비밀 값을 저장하려면 `.env`에 `ENCRYPTION_KEY`가 있어야 하고, 이 키를 바꾸면 저장된 값을 풀 수 없다. Gemini 키는 여기 넣지 않고 `.env`에만 둔다.

'승인과 한도' 탭의 '승인 모드'는 어떤 도구 호출을 실행 전에 확인할지 정한다. 기본은 첫째 줄이다.

| 승인 모드 | 승인을 묻는 것 | 어울리는 에이전트 |
|---|---|---|
| '셸·파이썬·패키지·쓰기 HTTP 승인' | 셸, 파이썬, 패키지 설치, GET·HEAD 외 HTTP 요청 | 대부분. 기본값(`all_shell`) |
| '쓰기 HTTP만 승인' | GET·HEAD 외 HTTP 요청만. 셸과 파이썬은 묻지 않고 실행 | 셸을 믿고 맡기는 파일 정리용 |
| '승인 없음' | 없음. 모든 도구를 묻지 않고 실행 | 지시문과 입력을 전부 믿을 수 있는 자동 실행용 |

컨테이너가 없어서 셸과 파이썬은 이 PC에서 내 권한으로 그대로 돈다. 그래서 기본이 가장 엄격한 첫째 줄이다. '승인 없음'을 고르면 '모델이 만든 명령이 이 PC에서 바로 실행됩니다.' 경고가, '쓰기 HTTP만 승인'을 고르면 '셸 명령은 작업공간 밖의 파일과 네트워크에도 닿을 수 있습니다.' 경고가 뜬다. 파일 도구와 HTTP GET은 어느 모드에서도 묻지 않는다. 파일 도구는 작업공간 밖 경로를 거부한다.

'한도'는 런 한 번이 쓸 수 있는 양이다. '최대 스텝'(모델 호출 횟수)은 기본 30이고 1~200이다. '최대 실행 시간(초)'은 기본 1800이고 승인이나 답을 기다린 시간은 빼고 센다. '런당 토큰 예산'은 기본 2,000,000이다. '런당 비용 상한(USD)'은 모델 가격을 입력해 둔 경우에만 적용된다. 대화가 '압축 기준(토큰)'을 넘으면 앞부분을 요약하고 '이전 대화가 요약되었습니다'라고 표시한다. '도구 1회 타임아웃(초)'은 기본 120이다.

스텝 한도에 닿으면 '스텝 한도(30)에 닿아 멈췄습니다'라고 알리고 런은 정상으로 끝난다. 이어서 하려면 메시지를 한 번 더 보낸다. '작업공간 프로세스'의 '메모리 상한(MB)'과 '최대 프로세스 수'는 비우면 서버 설정값(`SANDBOX_MEMORY_LIMIT_MB`와 `SANDBOX_MAX_PROCESSES`, 기본 1024MB와 64개)이고 서버 설정보다 클 수 없다. 새 에이전트의 기본 한도와 승인 모드는 설정의 '워크스페이스' 화면에서 바꾼다.

## 미리보기에서 써 보기

빌더 오른쪽의 '미리보기' 패널이 시험 채팅이다. 위쪽에 '초안 기준' 배지와 승인 모드 칩('승인: 셸·쓰기 HTTP' 같은)이 붙는다. 미리보기는 저장된 초안으로 돈다. 고치고 저장하지 않았으면 '저장하지 않은 변경은 미리보기에 반영되지 않습니다. 미리보기는 저장된 초안으로 실행합니다.'라는 안내가 뜬다.

세션은 첫 메시지를 보낼 때 만들어지고 에이전트별로 이 브라우저에 기억된다. 새로 고침해도 같은 대화가 열리고, 다른 브라우저에서 열거나 사이트 데이터를 지우면 새 대화로 시작한다. 지난 대화는 로그에 남아 있다.

아래 입력칸에 쓰고 Enter로 보낸다. 줄을 바꾸려면 Shift+Enter다. '파일 첨부' 버튼(클립 모양)으로 파일을 붙일 수 있다. 한 번에 20개, 파일당 100MB까지이고, 올린 파일은 작업공간의 `uploads` 폴더에 들어가며 내 메시지 아래에 내려받기 링크로 남는다.

위쪽 상태 표시줄에는 '실행 중', '완료' 같은 런 상태와 스텝, 토큰, 경과 시간, 쓰고 있는 모델이 나온다. 런은 한 번에 하나씩 돌아서 앞 런이 있으면 '대기열 2번째'처럼 기다린다. 도는 동안 '보내기' 자리에 '중지'가 나온다.

에이전트가 도구를 부르면 대화 사이에 도구 카드가 생긴다. 눌러서 펼치면 '입력', '출력', '종료 코드 0' 같은 결과가 보인다. 출력이 길어 앞부분이 생략됐으면 '전체 출력 내려받기'가 있다.

셸, 파이썬, 패키지 설치, GET·HEAD가 아닌 HTTP 요청 직전에는 런이 멈추고 도구 카드 아래에 '실행 승인 요청' 카드가 뜬다. 런 상태는 '입력 기다리는 중'이다. 카드에는 도구 이름, '작업 디렉터리', '타임아웃'과 함께 명령이나 코드 전문이 잘리지 않고 나온다. 승인하는 내용과 실행되는 내용이 같으니 끝까지 읽는다.

작업공간 밖 경로, `.env`를 건드리는 명령, 처음 보는 주소로 무언가를 보내는 명령, 모르는 패키지가 보이면 '거절'을 누른다. 괜찮으면 '승인'을 누른다. '거절 사유 (선택)'에 적은 말은 에이전트에게 전해져서 다른 방법을 찾게 한다. 키보드 단축키와 자동 포커스는 오승인을 막으려고 일부러 없다.

카드에 보이는 것은 명령까지이고 그 명령이 실행하는 스크립트 파일의 내용은 안 보인다. 작업공간의 스크립트를 돌리는 명령이면 그 파일을 쓴 `write_file` 도구 카드를 먼저 열어 본다.

카드의 '이 세션에서는 묻지 않기'를 켜고 승인하면 그 세션의 이후 도구 호출이 승인 없이 실행된다. 위쪽에 '자동 승인 켜짐' 표시가 붙고, 옆의 '끄기'로 되돌린다. 에이전트 설정은 그대로 두고 이 세션만 푸는 것이라 편하지만, 모델이 만든 명령이 바로 돈다는 점은 '승인 없음'과 같다. 켠 세션은 로그에도 '자동 승인'으로 표시된다. 같은 시험을 되풀이할 때가 아니면 켜지 않는다.

승인 카드가 떠 있는 동안에는 입력칸이 잠겨서 새 메시지를 보낼 수 없다. API로 보내면 409(`run_in_progress`)로 거절되고 안내는 "이 세션에서 진행 중인 런이 있다. 끝나거나 승인·답을 받은 뒤 다시 보낸다"다. 승인하거나 거절하거나 '중지'를 누른다.

기본 24시간 안에 답이 없으면 '응답을 기다리는 시간이 지나 런이 취소되었습니다'로 끝난다. 승인을 기다리는 중에 새로 고쳐도 카드가 그대로 돌아온다.

에이전트가 `ask_user`로 물으면 '에이전트의 질문' 카드가 뜬다. 보기가 있으면 버튼으로 나오고, 누르면 그 답이 바로 전송된다. 직접 쓰는 답은 카드의 입력칸에 쓰고 '답 보내기'를 누른다. 아래 입력칸에 그냥 써도 질문의 답으로 가며, 그때 입력칸 안내가 '여기에 쓰면 질문에 대한 답으로 보냅니다'로 바뀐다. 에이전트가 보기만 고르게 한 질문에는 직접 쓰는 칸이 없고 버튼으로만 답한다. 답에는 파일을 붙일 수 없다.

'중지'는 실행 중인 런, 대기열의 런, 승인이나 질문을 기다리는 런에 모두 쓸 수 있다. 실행 중이던 도구는 그 자손 프로세스까지 끝나고, 런은 '중지됨', 도구 카드는 '취소됨'으로 바뀐다.

런이 만들거나 고친 파일은 대화 아래 '변경된 파일' 목록에 나오고 내려받기 아이콘으로 받는다. 받는 것은 서버가 따로 보관한 사본이라 작업공간을 지워도 받을 수 있다. 파일당 50MB, 런당 200개·200MB까지만 보관하고 넘으면 '너무 커서 보관하지 않음' 같은 표시가 붙는다.

패널 위쪽의 하드디스크 아이콘('작업공간 보기')은 이 세션의 작업공간 창을 연다. 첫 메시지로 세션이 생기기 전에는 눌리지 않는다. 창에는 '상태', '경로', '디스크'(사용량 / 한도와 막대), '마지막 실행', '실행 중 프로세스' 표, '큰 폴더' 목록이 있다. 프로세스 표에는 종류, PID, 경과 시간, 메모리 최고 요청치가 나오고 줄마다 종료 버튼이 있다.

창의 버튼은 셋이다. '프로세스 종료'는 도는 도구 프로세스를 모두 끝낸다. '패키지 삭제'는 설치한 패키지와 캐시를 비우고 설치 이력은 남겨서 필요하면 다시 설치하게 한다. '작업공간 초기화'는 폴더를 지우고 첨부 파일과 스킬만 다시 채우므로 에이전트가 만든 파일과 설치한 패키지가 사라지고, 대화 기록과 보관된 결과 파일은 남는다. 런이 도는 동안은 뒤의 둘을 누를 수 없다.

작업공간이 디스크 한도(기본 2GB)를 넘으면 창에 '디스크 한도를 넘었습니다'가 뜨고 그 세션의 새 메시지는 `workspace_disk_limit`(409)로 거부된다. '패키지 삭제'나 '작업공간 초기화'로 줄이면 다시 보낼 수 있다. 세션별 크기는 설정의 '작업공간' 화면에서 목록으로 본다.

패널 위쪽의 '세션 초기화' 버튼은 새 대화를 시작한다. 도는 런이 있으면 '새 대화 시작' 창이 뜨고 '새로 시작'을 누르면 런을 멈추고 새 세션으로 간다. 지금 대화는 지워지지 않고 로그에 남는다. 이전 세션은 빌더의 '에이전트 로그'에서 소스가 '미리보기'인 세션으로 열어 읽는다. 미리보기에서 다시 이어 쓰지는 못한다.

그 밖에 자주 보는 안내가 몇 개 있다. '연결이 끊겨 다시 연결하는 중 (2/5)'는 화면이 서버와의 스트림을 다시 잇는 중이라는 뜻이고, 끝내 못 이으면 '실시간 연결을 되살리지 못했습니다. 새로 고침해 보세요.'가 나온다. '작업공간을 발행 스냅샷에서 복원하는 중'은 발행한 에이전트의 첫 대화에서 파일과 패키지를 되살리는 중이다. '초안이 바뀌어 새 지시문으로 이어서 실행합니다'는 대화 도중 저장한 초안의 지시문이나 도구가 다음 런부터 적용된다는 알림이다. '런이 실패했습니다'에는 오류 코드가 붙고, 모델이 막힌 경우에는 '잠시 뒤 다시 보내 볼 수 있습니다.'가 같이 나온다.

## 발행과 밖에서 쓰기

이 장은 에이전트 기준이고 워크플로우는 '워크플로우 발행과 밖에서 쓰기'에 따로 적었다. 미리보기가 마음에 들면 '발행' 탭으로 간다. 발행은 저장된 초안을 번호가 붙은 버전(v1, v2…)으로 굳히는 일이다. 웹앱과 API는 초안이 아니라 발행 버전만 쓰므로, 발행하기 전까지 밖에서는 아무것도 바뀌지 않는다. 저장하지 않은 변경이 있으면 '저장하지 않은 변경이 있습니다. 먼저 저장하세요.'가 뜨고 버튼이 막힌다. '변경 메모'(선택)를 적고 '발행'을 누른다.

발행하면 이 에이전트의 가장 최근 미리보기 작업공간(에이전트가 만든 파일과 스크립트)이 스냅샷으로 묶여 그 버전에 붙는다. 미리보기를 한 적이 없으면 직전 발행 버전의 스냅샷을 그대로 이어받는다. 그래서 미리보기에서 데이터를 준비해 두고 발행하면, 웹앱과 API의 새 대화가 그 파일이 있는 작업공간에서 시작한다. 첨부 파일, 스킬, 설치한 패키지는 스냅샷에 넣지 않고 새 대화를 시작할 때 다시 채우므로 첫 대화가 조금 느릴 수 있다.

미리보기에서 런이 도는 중이면 "미리보기에서 런이 실행 중이다. 끝난 뒤 발행한다"로 거절되니 끝난 뒤에 한다. 발행할 때는 초안을 한 번 더 검사한다. 저장 뒤에 지운 스킬처럼 문제가 생긴 설정이 있으면 "초안에 발행할 수 없는 설정이 있다"로 거절되고 고칠 곳이 함께 나온다.

'발행 이력'에는 버전, 메모, 시각이 나오고 지금 쓰는 버전에 '현재 발행' 표시가 붙는다. 이전 버전의 '이 버전으로 되돌리기'를 누르고 확인하면 그 버전이 현재 발행 버전이 된다. 초안은 바뀌지 않는다. 이미 시작된 웹앱·API 대화는 만들 때의 버전으로 계속되고 새 대화부터 되돌린 버전을 쓴다.

웹앱은 'API' 탭 맨 위 '웹앱' 패널에서 '웹앱으로 공개'를 켜면 열린다. 발행한 에이전트에만 나타나고 기본은 꺼져 있다. 켜면 `http://127.0.0.1:8500/apps/<슬러그>` 주소가 나오고 '링크 복사'와 '열기'를 쓸 수 있다. 끄면 그 주소는 404가 된다. 웹앱도 같은 계정으로 로그인해야 열린다.

웹앱 화면은 왼쪽에 '새 대화' 버튼과 대화 목록, 가운데에 채팅이 있다. 대화 제목은 첫 메시지의 첫 줄에서 따온다. 위쪽에 에이전트 이름, 발행 버전 배지(v2 같은), 승인 모드 칩이 보인다. 승인 카드, 질문 카드, 파일 내려받기는 미리보기와 같다. 다시 발행한 뒤 예전 대화를 열면 '이전 발행 버전' 배지가 붙고 그 대화는 만들 때의 버전으로 이어진다. 지금 버전으로 이야기하려면 '새 대화'로 시작한다. 왼쪽 아래 '콘솔로 돌아가기'는 에이전트 목록으로 간다.

같은 'API' 탭의 'API 키' 패널에서 '키 만들기'를 누르고 '키 이름'(예: 정리 스크립트)을 넣으면 '키를 만들었습니다' 창에 키 원문이 나온다. 창에는 '이 값은 지금 한 번만 보여 줍니다. 안전한 곳에 복사해 두세요.'라는 안내가 붙는다. 창을 닫으면 다시 볼 수 없고 목록에는 '앞부분'만 남으니, 잃어버리면 새로 만든다.

'폐기'를 누르면 그 키로 오는 호출은 바로 401을 받는다. 키는 에이전트 하나에 묶여 그 에이전트의 발행 버전만 부를 수 있고, 키당 분당 60회로 제한된다. 넘으면 429와 `Retry-After`가 온다. 키는 `.env`처럼 다룬다. 특히 '승인 없음'으로 발행한 에이전트의 키는 이 PC에서 명령을 실행하는 열쇠나 다름없으니 쓰지 않으면 폐기한다. 키가 맞는지는 `GET /api/v1/info`로 본다.

API 탭 아래 '호출 예시'에 curl 네 개가 있고 복사 버튼이 붙어 있다. Git Bash에서 `API_KEY=발급한_키`를 먼저 넣고 실행한다. 한글 본문은 here-document로 넘기는 형태라 Windows의 curl에서도 깨지지 않는다. 가장 단순한 것은 메시지를 보내고 끝날 때까지 기다리는 호출이다.

```bash
curl http://127.0.0.1:8500/api/v1/chat-messages \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @- <<'JSON'
{"query":"작업공간에 어떤 파일이 있는지 알려줘","user":"me","response_mode":"blocking"}
JSON
```

`response_mode`를 `streaming`으로 바꾸고 `curl -N`으로 부르면 토큰과 도구 이벤트가 SSE로 흘러온다. 응답의 `conversation_id`를 다음 요청에 같이 보내면 같은 대화가 이어진다. `user`는 호출하는 쪽을 구분하는 이름표이고, 대화 목록은 `GET /api/v1/conversations?user=me&limit=20`으로 본다.

승인 모드가 기본이면 에이전트가 셸을 쓰는 순간 응답이 `"status":"waiting_input"`으로 끝나고 `pending_interaction`이 담긴다. `POST /api/v1/chat-messages/<run_id>/input`에 `{"decision":"approve"}`를 보내야 이어진다. 사람 없이 돌릴 에이전트는 '승인 없음'으로 발행하는데, 위험을 알고 하는 선택이다. `scripts/smoke-api.sh`가 이 흐름을 한 번 훑어 준다.

과업은 대화가 아니라 한 번 시키고 결과를 받는 호출이다. `instruction`의 `{{이름}}`을 `inputs`로 채워 에이전트에게 주고, `output_schema`(JSON Schema)가 있으면 에이전트가 그 모양의 JSON을 제출할 때까지 일해서 `result`에 담아 돌려준다.

```bash
curl http://127.0.0.1:8500/api/v1/agent-tasks \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @- <<'JSON'
{"instruction":"{{a}}와 {{b}}를 더한 값을 sum에 담아 제출한다","inputs":{"a":2,"b":3},
 "output_schema":{"type":"object","properties":{"sum":{"type":"integer"}},"required":["sum"],"additionalProperties":false},
 "user":"me","response_mode":"blocking"}
JSON
```

스키마에 맞지 않으면 다시 제출하게 하고, 끝내 못 맞추면 `output_invalid`, 제출 없이 끝나면 `output_missing`으로 실패한다. 스키마의 최상위는 `type: object`이고 `additionalProperties: false`여야 한다. 기본은 끝나면 작업공간을 지우는 일회성(`session_mode`가 `ephemeral`)이고 결과 파일은 남아서 응답의 `files`로 받는다. 과업도 발행 버전의 승인 모드를 따른다.

## 스킬

스킬은 `SKILL.md`와 참고 자료·스크립트를 묶은 폴더(zip)다. 지시문에 다 담기 어려운 절차를 스킬로 두면, 에이전트가 일이 스킬 설명에 맞을 때 작업공간의 `skills/<이름>/SKILL.md`를 읽고 따른다. zip 안에는 최상위 폴더 하나가 있거나 루트에 `SKILL.md`가 있어야 하고, `SKILL.md`는 `---`로 둘러싼 머리말에 `name`(영문 소문자·숫자·하이픈, 64자까지)과 `description`(1024자까지)을 쓴다. `description`은 에이전트가 언제 이 스킬을 쓸지 판단하는 근거다.

```markdown
---
name: csv-report
description: CSV 파일을 읽어 요약표를 만들 때 쓴다
---
여기부터 절차를 적는다. 스크립트는 같은 폴더에 두고 run_python으로 실행하게 한다.
```

패키지는 50MB, 파일 2000개까지이고 `SKILL.md` 하나는 32KB를 넘을 수 없다. '스킬' 화면의 '스킬 올리기'로 zip이나 `.skill` 파일을 올리면 라이브러리에 v1로 들어간다. 카드의 '내용 보기'로 파일을 열어 볼 수 있다.

같은 이름을 다시 올리면 "같은 이름의 스킬이 이미 있다"로 막히고, 카드 오른쪽 점 세 개 메뉴의 '새 버전 올리기'로 올려야 v2가 된다. 이때 `name`은 같아야 한다. 삭제도 같은 메뉴에 있고, 지워도 이미 발행한 버전은 계속 쓴다.

에이전트에는 빌더의 '도구와 스킬' 탭에서 붙인다. '라이브러리 스킬'에서 체크하면 그 순간의 버전으로 고정되고, 스킬에 새 버전을 올려도 에이전트는 바뀌지 않는다. 새 버전을 쓰려면 'v1이(가) 고정되어 있습니다.' 옆의 '최신 버전으로'를 누른다. 한 에이전트만 쓰는 스킬은 '이 에이전트 전용 스킬'의 '전용 스킬 올리기'로 올린다. 이름이 겹치면 전용 스킬이 이긴다. 올리면 '초안을 저장해야 이 스킬이 들어갑니다.'라는 안내가 뜨니 저장하고, 웹앱과 API에 반영하려면 발행한다.

## 로그와 사용량

'로그'에는 미리보기, 웹앱, API, 과업 어디서 한 대화든 쌓인다. 위쪽 탭은 대화 단위의 '세션'과 메시지 하나를 처리한 실행 단위의 '런'이고, 워크플로우의 기록은 세 번째 탭 '워크플로우 런'에 따로 모인다(뒤의 '워크플로우 실행과 실행 기록'). 필터는 '에이전트', '소스', '기간'이 있고 '런' 탭에서만 '상태'가 더해진다. 소스는 '미리보기', '웹앱', 'API', '과업'이고 기간은 '전체'와 '최근 24시간'부터 '최근 90일'까지다. 필터는 주소에 남아서 새로 고침해도 유지되고 '필터 지우기'로 푼다. 목록은 '더 보기'로 이어 불러온다. 한 에이전트의 기록만 보려면 빌더의 '에이전트 로그'를 쓴다.

목록에서 제목을 누르면 세션 상세가 열린다. 위쪽 머리에 '에이전트', '버전'('초안' 또는 v번호), '소스', 'API 키', '외부 사용자', '승인'('자동 승인' 또는 '에이전트 설정을 따름'), '메시지 수', '세션 ID'가 있다. 왼쪽 '메시지'는 대화 전문이고, 오른쪽에 '런' 목록과 '런 인스펙터', 작업공간 패널이 있다.

런을 고르면 인스펙터에 상태, 모델(폴백이 일어났으면 '폴백' 배지), 스텝, 토큰, 비용, 걸린 시간이 나오고 탭이 셋이다. '스텝' 탭은 모델 호출마다 쓴 토큰과 키 번호, 그 스텝의 도구 호출을 순서대로 보여 준다. 도구 호출을 펼치면 입력, 출력 발췌(앞 24KB와 뒤 8KB), 종료 코드, 소요 시간, 메모리 최고 요청치가 나오고 출력이 크면 '전체 보기'와 '내려받기'가 있다.

'승인·질문 2' 탭(숫자는 건수)은 승인 결정('승인함', '거절함: 사유')과 질문-답을 모은다. '원본 이벤트 31' 탭은 서버가 기록한 이벤트를 번호, 시각, 종류, 내용으로 보여 주고 종류('예: tool_call')로 거를 수 있다. 에이전트가 이상하게 굴 때는 스텝 탭에서 어느 도구 결과를 읽은 뒤 그렇게 했는지 거슬러 올라간다.

로그 화면에서는 승인에 답할 수 없다(워크플로우 런 상세는 예외다). 대기 중인 런은 빌더 미리보기나 웹앱에서 답한다. 이벤트와 도구 출력 파일은 보존 기간(기본 90일)이 지나면 지워지고 메시지와 런 요약은 남는다.

사용량은 설정의 '사용량'에 있다. 런마다 기록된 토큰과 비용을 '일별', '에이전트별', '모델별', '워크플로우별'로 더해 보여 주고 기간은 '최근 7일', '최근 30일', '최근 90일', '이번 달', '지난달'에서 고른다. 비용은 설정의 '워크스페이스'에서 '모델 가격'(100만 토큰당 USD)을 넣은 뒤에 실행한 런부터 계산된다. 가격이 없으면 토큰 수만 보이고, 나중에 가격을 넣어도 지난 런의 비용은 바뀌지 않는다. '추정' 표시는 응답에 사용량이 없어 글자 수로 센 토큰이 섞였다는 뜻이다. 모델별 집계는 폴백이 있었어도 그 런이 마지막으로 쓴 모델에 몰린다.

## 설정

'LLM'(Gemini 연결) 화면의 키 정보는 `.env`의 `GEMINI_API_KEYS`에서만 읽고, 화면에는 번호와 끝 4자리만 나온다. '연결 정보'에 엔드포인트, 키 개수, '429 뒤 쉬는 시간', '모델 폴백 순서'가 있다. '키 상태' 표는 키마다 '정상', '14:32까지 쉼'(429를 받아 잠시 쉬는 중), '사용 중지 (401·403)'와 성공·실패·429 횟수를 보여 준다. 횟수는 서버를 다시 띄우면 처음부터 센다. 401이나 403을 받은 키는 서버를 다시 띄울 때까지 쓰지 않는다.

'연결 테스트'는 모델 목록을 받고 짧은 생성 호출을 한 번 하므로 토큰을 조금 쓴다. 성공하면 '연결됐습니다'와 모델 수, 쓴 키, 응답이 나온다. 키를 바꾸거나 더하려면 `.env`의 `GEMINI_API_KEYS`를 쉼표로 이어 고치고 서버를 다시 띄운다. 앞의 키부터 쓰다가 429를 받으면 다음 키로 넘어간다.

'워크스페이스' 화면에서는 '이름', '런 이벤트 보관 기간(일)'(기본 90, 1~3650), '기본 승인 모드', '기본 한도', '모델 가격'을 고치고 '저장'을 누른다. 기본 승인 모드와 기본 한도는 앞으로 만들 에이전트에만 적용되고 이미 있는 에이전트는 그대로다. 모델 가격에서 '캐시 입력'을 비우면 입력 단가의 25%로 계산한다.

'작업공간' 화면은 세션마다 생긴 작업공간 폴더의 전체 목록이다. 세션, 에이전트, 상태('대기', '런 실행 중'), 크기('한도 초과' 표시 포함), 실행 중 프로세스, 마지막 활동이 나온다. 줄 끝의 점 세 개 메뉴에서 '프로세스 종료', '패키지 삭제', '초기화', '세션 로그 보기'를 쓴다. 끝난 세션의 작업공간은 자동으로 지워지지 않으니 디스크가 차면 여기서 큰 것부터 '패키지 삭제'나 '초기화'로 줄인다. 크기는 런이 끝날 때 잰 값이다.

'HTTP 허용 목록'은 에이전트의 `http_request` 도구와 워크플로우의 'HTTP 요청' 노드, '도구' 노드의 '웹 페이지 가져오기'가 접속할 수 있는 호스트다. GET은 승인 없이 나가므로 이 목록이 유일한 문이다. 화면에서는 보기만 하고, 고치려면 화면의 '경로'에 나온 파일(보통 `DATA_DIR`의 `allowlist.txt`)을 편집기로 열어 한 줄에 하나씩 적고 저장한다. 몇 초 안에 반영되어 서버를 다시 띄울 필요가 없고, 화면의 '다시 읽기'로 '읽은 규칙'을 확인한다. 처음 뜰 때 PyPI와 GitHub만 든 기본 파일을 만든다.

```text
# 줄 시작이 #이면 주석
api.example.com
# 앞의 점은 하위 도메인 전부(example.org 자신은 빠진다)
.example.org
```

`*` 한 줄은 모든 공개 호스트를 열어 버리니 꼭 필요할 때만 쓴다. 사설·루프백 주소와 IP 주소는 `*`로도 열리지 않는다. 셸과 파이썬이 직접 여는 네트워크는 이 목록과 상관없고 승인 모드가 막는다. 'HTTP 요청' 노드는 POST 같은 메서드도 승인 없이 보내서 `*`가 더 위험하다.

'내 계정'에서는 '계정 정보'를 보고 '비밀번호 바꾸기'(현재 비밀번호와 새 비밀번호, 12자 이상)와 '로그아웃'을 한다. 바꾸면 이 브라우저를 뺀 다른 곳의 로그인은 끊긴다. 비밀번호를 잊었으면 서버를 끄고 터미널에서 `uv run platform reset-password`를 돌린다. 새 비밀번호를 두 번 묻고, 바꾸면 모든 로그인이 끊기니 브라우저에서 다시 로그인한다.

## 워크플로우 만들기

워크플로우는 노드를 이어 그린 실행 흐름이다. 에이전트는 모델이 도구를 골라 가며 일하지만, 워크플로우는 어떤 노드를 어떤 순서로 돌릴지 내가 미리 정해 둔다. 종류가 둘이다. '워크플로우'는 입력을 받아 그래프를 한 번 실행하고 '끝' 노드가 고른 값을 돌려준다. '챗플로우'는 대화에서 메시지를 받을 때마다 그래프를 한 번 실행하고 '답변' 노드가 답을 보낸다. 종류는 만들 때 정하고 나중에 바꿀 수 없다. 이 장은 둘이 함께 쓰는 편집기를 다루고, 챗플로우에만 있는 것은 '챗플로우' 장에 따로 적었다.

여기서 런은 그래프를 한 번 실행한 것이고, 노드 런은 그 안에서 노드 하나가 한 번 돈 기록이다. 반복 안의 노드는 원소마다, 루프 안의 노드는 회차마다 노드 런이 생긴다. 에이전트의 런·스텝과는 다른 단위다.

왼쪽 메뉴의 '워크플로우'에 만든 것이 카드로 나온다. '이름이나 설명으로 찾기'로 거르고 '종류'로 '워크플로우'나 '챗플로우'만 본다. 카드에는 종류, '초안만' 또는 'v2 발행', 슬러그, 수정 시각이 붙고 점 세 개 메뉴에 '실행 기록'과 '워크플로우 삭제'가 있다. 지우면 그 워크플로우의 API 키는 바로 폐기되고 웹앱 주소도 열리지 않는다. 런 기록은 남지만 로그의 '워크플로우 런' 탭에는 더 보이지 않는다. 목록의 '가져오기'는 DSL 파일로 만드는 것이라 뒤의 'DSL 내보내기·가져오기'에서 설명한다.

'새 워크플로우'를 누르면 '이름'(필수), '종류', '아이콘', '슬러그', '설명'을 묻는다. 챗플로우를 고르면 '처음 그래프'도 고른다. '빈 그래프'는 시작과 답변 노드만 두고, '기본 대화'는 '시작 → LLM → 답변'이라 만들자마자 대화할 수 있다(LLM의 대화 기억이 켜져 있다). 워크플로우의 빈 그래프는 '시작 → 끝'이다. 슬러그는 웹앱 주소 `/flows/슬러그`에 들어가고, 비우면 이름에서 만든다(한글뿐인 이름이면 `workflow`로 시작하고 겹치면 `-2`가 붙는다). 만들면 편집기가 열린다.

편집기(`/workflows/<id>`)에서는 왼쪽 메뉴가 접혀 있고 위쪽 띠의 '메뉴 펼치기' 단추로 연다. 가운데가 캔버스이고 왼쪽에 '노드' 팔레트, 오른쪽에 패널이 있다. 패널의 탭은 '노드'(고른 노드의 설정), '실행'(챗플로우는 '미리보기'), '변수', '설정', '발행', 'API'다. 위쪽 띠에는 종류 배지, 저장 상태, 검증 표시, '실행 기록', 'DSL', '실행'(챗플로우는 '미리보기'), '발행'이 있고 맨 끝 버튼이 오른쪽 패널을 여닫는다.

노드는 팔레트에서 캔버스로 끌어 놓거나 눌러서 더한다. 노드를 골라 둔 채 팔레트의 노드를 누르면 그 뒤에 이어 붙는다. 팔레트는 '입력·출력', '모델', '흐름', '변환·도구'로 나뉘고 '노드 찾기'로 거른다. 노드끼리는 나가는 핸들에서 들어가는 핸들로 끌어 잇는다. 자기 자신, 시작 노드로 들어오는 연결, 이미 있는 연결, 순환이 생기는 연결은 이어지지 않고 연결은 300개까지다. 노드나 연결을 눌러 고른 뒤 Delete 키로 지운다. 도구 모음에는 확대, 축소, '화면에 맞추기', 실행 취소(Ctrl+Z), 다시 실행(Ctrl+Shift+Z)이 있다. 실행 취소는 그래프만 50단계까지 되돌리고 '변수'·'설정' 탭의 값은 되돌리지 않는다.

노드를 누르면 '노드' 탭에 설정이 열리고 주소가 `?node=<노드 id>`로 바뀐다. 그 주소를 다시 열면 같은 노드가 골라진다. 설정 폼에는 저장 단추가 없고 고치는 대로 그래프에 반영된다. 카드에는 제목과 설정 요약 한 줄이 보이고, 검증에 걸리면 '오류 N개'나 '경고 N개'가 붙는다. '조건 분기'와 '질문 분류'는 가지마다 핸들이 있다.

모든 노드는 id를 가진다. `llm_1`, `template_1`처럼 종류와 번호로 붙고, 변수를 부를 때 이 id를 쓴다. '노드' 탭 맨 위의 '노드 id'에서 바꿀 수 있고, 바꾸면 이 노드를 가리키던 참조가 같이 고쳐진다. 영문 소문자로 시작해 소문자·숫자·밑줄로 32자까지 쓰고 `sys`, `env`, `conv`는 쓸 수 없다.

'LLM', '질문 분류', '파라미터 추출', '에이전트', 'HTTP 요청', '코드', '도구' 노드에는 '오류 처리와 재시도'가 있다. 실패했을 때 '런을 실패로 끝냄'(기본), '기본 출력값으로 계속', '실패 가지로 보냄' 중에 고른다. 마지막을 고르면 카드에 '실패하면' 핸들이 생기고 거기에 이은 노드로 간다. 재시도는 0~5번, 간격 0~10000ms이고 일시 오류(429·5xx, 연결 오류, 시간 초과)일 때만 다시 한다. 나머지 노드는 실패하면 런이 끝난다.

팔레트에 나오는 노드는 열아홉 가지다. 워크플로우의 팔레트에는 '답변'이, 챗플로우의 팔레트에는 '끝'이 나오지 않는다. '변수 쓰기'는 워크플로우의 팔레트에서 '루프 안에서만' 표시가 붙고, 루프 틀 밖에 놓으려 하면 안내만 뜨고 놓이지 않는다. '사람 입력', '루프', '리스트 연산', '문서 추출', '도구'는 표 뒤에 따로 설명한다.

표에 넣지 못한 점이 몇 가지 있다. 'LLM'은 도구를 부르지 못하니 모델이 도구를 골라 쓰게 하려면 '에이전트' 노드를 쓴다. 'JSON 응답'은 읽지 못하면 한 번 다시 묻는다. '코드'는 표준 라이브러리만 쓰는 것을 전제로 하고 승인 없이 이 PC의 샌드박스에서 돈다. 반환값은 JSON으로 바꿀 수 있는 dict여야 하고 선언한 출력 이름이 모두 들어 있어야 한다. 시간은 기본 30초(`.env`의 `WF_CODE_TIMEOUT_SEC`, 노드에서 60초까지), 메모리는 256MB, 프로세스는 8개, 반환값은 256KB, print 출력은 1MB까지다. 'HTTP 요청'은 4xx·5xx 응답을 실패로 보지 않고 `status_code`로 내보낸다. 연결 오류와 시간 초과만 실패한다. 응답 본문이 1MB를 넘거나 바이너리면 `files`로 받고, 5MB를 넘으면 실패한다. JSON 본문에 글 변수를 넣을 때는 `{{ start.q | tojson }}`처럼 `tojson`을 붙여야 따옴표가 깨지지 않는다. 응답 본문을 LLM에 넘기면 본문 속 문장이 지시처럼 읽힐 수 있으니 믿을 수 없는 응답은 LLM 시스템 프롬프트에서 자료로만 다루게 한다.

'에이전트' 노드는 에이전트를 과업 모드(API의 `agent-tasks`와 같은 방식)로 불러 일을 맡긴다. '버전'을 '발행 버전(기본)'으로 두면 에이전트의 발행 버전을 쓰는데, 편집기에서 돌릴 때 발행 버전이 없으면 초안을 쓴다. 발행한 워크플로우(웹앱·API)는 발행 버전만 쓴다. '과업 지시'에는 변수를 넣고, 결과 형식을 'JSON'으로 하면 결과 JSON 스키마를 정해야 하며 그 모양의 값이 `result`에 담긴다. '승인'은 기본이 '에이전트 설정대로'다. '한도 덮어쓰기'는 켜고 채운 칸만 에이전트 버전의 한도 대신 쓴다. '세션'의 '대화마다 같은 세션'은 고를 수 있지만 지금은 '실행마다 새 세션'과 똑같이 돌고 노드 기록에 경고가 남는다.

사람이 확인하거나 입력해야 하는 단계에는 '사람 입력' 노드를 둔다. 이 노드에 닿으면 런이 멈추고 폼이 뜬다. '안내문'은 폼 위에 마크다운으로 보이는 글이고 `{{ llm_1.text }}`처럼 앞 노드의 값을 넣을 수 있다. '폼 필드'는 시작 노드의 입력 필드와 같은 방식으로 정하며 하나 이상 있어야 한다. 새로 놓으면 필수 여러 줄 글 칸 `reply`('답') 하나가 들어 있다. 받은 값은 필드 이름대로 노드의 출력이 되어 뒤 노드가 `{{ human_input_1.reply }}`처럼 읽는다. 폼이 어디에 뜨고 어떻게 답하는지는 '워크플로우 실행과 실행 기록'에 적었다. 이 노드는 'agent 노드 승인' 설정과 상관없이 늘 멈추고, 나란히 도는 가지에 폼이 둘이면 한 번에 하나씩 뜬다.

'리스트 연산'은 배열 하나를 '거르기', '정렬', '자르기' 순서로 처리하고 '하나 꺼내기'로 원소 하나를 고른다. 단계마다 스위치가 있고 켠 것만 한다. '거르기'의 조건 줄은 key, 연산자, '비교 값'이고 연산자는 '조건 분기'와 같다. 줄이 둘 이상이면 '모두 맞으면'이나 '하나라도 맞으면'으로 묶는다. key를 비우면 원소 자체를 비교하고, 객체 배열이면 키 이름을 쓴다(`a.b`처럼 점으로 하위 키). 파일 배열은 key를 '이름', '크기(바이트)', 'MIME 형식', '확장자' 중에서 고르며 확장자는 점 없는 소문자(`pdf`)로 비교한다. '정렬'은 key와 방향('오름차순', '내림차순')을 정하는데, key 값이 없는 원소는 방향과 상관없이 뒤로 간다. '자르기'는 '건너뛸 수'와 '남길 수'를 정하고 '남길 수'를 비우면 끝까지다. '하나 꺼내기'의 '자리'는 0부터 세고 음수면 뒤에서 센다. `result`는 처리한 배열, `count`는 그 원소 수, `first_record`와 `last_record`는 처음과 마지막 원소, `item`은 꺼낸 원소이며 자리가 범위 밖이면 null이다.

파일 속 글이 필요하면 '문서 추출'을 쓴다. '파일 변수'에는 파일 하나나 파일 목록을 고른다. 시작 노드의 '파일'·'파일 여러 개' 필드, 챗플로우의 `sys.files`, 'HTTP 요청'과 '에이전트' 노드의 `files`가 그런 변수다. 한 번에 20개, 파일 하나에 50MB까지 읽는다. docx의 표는 마크다운 표로 바뀌고, pdf는 문서에 든 글만 꺼내서 그림 속 글자는 읽지 못한다. 파일이 하나면 `text`가 그 글이고, 여럿이면 파일마다 '## 파일 이름' 머리글을 붙여 이은 글이다. `texts`에는 파일마다 따로 담긴다. 합친 글이 1MB를 넘으면 앞부분만 담고 경고를 남기며, 읽지 못하는 파일이 하나라도 있으면 노드가 실패한다. pdf와 docx는 처음 쓸 때 서버가 파서를 내려받아 두기 때문에 첫 실행은 수 초 걸리고 인터넷이 필요하다. 설치가 안 될 때는 '운영과 문제 해결'을 본다.

'도구' 노드는 서버에 들어 있는 내장 도구를 그래프의 정해진 자리에서 부른다. 에이전트 빌더의 도구와 달리 모델이 고르지 않고 승인도 묻지 않는다. 도구를 고르면 매개변수 칸이 나오고, 칸마다 값 방식을 정한다. '템플릿'은 글에 `{{ }}` 변수를 섞고, '변수'는 변수 하나를 그대로 넘기고, '고정값'은 적은 값을 쓴다. 방식을 바꾸면 칸이 비워진다. 비워 둔 칸은 도구의 기본값을 쓰고, 기본값 없는 필수 칸이 비면 검증 오류다.

| 도구 | 매개변수 | 출력 |
|---|---|---|
| '현재 시각' (`current_time`) | '시간대'(`local`, `UTC`, `+09:00`, `Asia/Seoul` 꼴. 기본은 이 PC의 시간대), '형식'(strftime 꼴, 예: `%Y-%m-%d %H:%M`. 비우면 ISO 8601) | `text`, `iso`, `date`, `timestamp`, `timezone` |
| 'JSON 읽기' (`json_parse`) | 'JSON 글', '경로'(예: `items[0].name`. 비우면 전체) | `value`, `text`, `type`, `found` |
| '정규식 추출' (`regex_extract`) | '글', '정규식'(파이썬 `re` 문법), '플래그'(`i`, `m`, `s`), '그룹'(번호나 이름. 비우거나 0이면 맞은 부분 전체) | `text`(처음 맞은 부분), `matches`(전부), `count`, `found` |
| '웹 페이지 가져오기' (`web_fetch`) | '주소'(http·https), '최대 글자 수'(기본 100000) | `text`, `title`, `url`, `status_code`, `content_type` |

'현재 시각'의 시간대는 이름으로 쓰면 `Asia/Seoul`처럼 서머타임 없는 아시아 몇 곳만 확실히 알아듣는다. 그 밖의 이름은 찾지 못할 수 있으니 `+09:00` 같은 오프셋을 쓴다. 'JSON 읽기'는 경로에 값이 없어도 실패하지 않고 `found`가 false, `value`가 null이며, JSON이 아니면 `invalid_json`으로 실패한다. '정규식 추출'은 글 1MB, 정규식 512자, 맞은 부분 1,000개까지 본다. '웹 페이지 가져오기'는 설정의 'HTTP 허용 목록'에 있는 호스트만 부른다. HTML은 태그를 떼고 글만 남겨 제목을 `title`로 따로 주고, pdf나 이미지처럼 글이 아닌 응답은 `unsupported_content_type`으로 실패하니 'HTTP 요청'으로 받아 '문서 추출'로 읽는다. 4xx·5xx 응답은 실패가 아니라 `status_code`로 나오고 응답은 5MB까지 받는다. '최대 글자 수'보다 긴 글은 앞부분만 남기고 경고가 붙는다. 가져온 글을 LLM에 넘길 때의 주의는 'HTTP 요청'과 같다.

텍스트 칸(프롬프트, 답변, URL, 헤더, 본문, 템플릿 같은)에서는 `{{ 노드id.출력이름 }}`으로 앞 노드의 출력을 넣는다. `{{ start.q }}`, `{{ llm_1.text }}`, `{{ http_1.json.items[0] }}`처럼 쓴다. 프롬프트 칸에서 `{{`를 치면 변수 목록이 열린다. 끝 노드의 출력이나 조건의 변수처럼 변수를 고르는 칸은 '변수 고르기' 목록에서 고르거나 '직접 입력'에 `llm_1.text` 꼴로 쓴다. 쓸 수 있는 것은 연결을 따라 거슬러 닿는 앞 노드의 출력뿐이다. 예약된 이름이 셋 있다.

- `sys`: 시스템 값. 모든 런에 `sys.workflow_id`, `sys.run_id`, `sys.kind`(workflow 또는 chatflow), `sys.now`(UTC 시각)가 있다. 챗플로우에는 `sys.query`(사용자 메시지), `sys.files`(첨부 파일), `sys.conversation_id`, `sys.message_id`, `sys.user`(API로 부른 사용자 이름이고 미리보기·웹앱은 비어 있다), `sys.turn`(몇 번째 메시지인지, 1부터)이 더해진다.
- `env`: '변수' 탭의 환경 변수. `{{ env.API_BASE }}`로 읽는다. 입력 화면은 에이전트의 환경변수와 같다. '비밀'로 표시한 값은 암호화해 저장하고 다시 보여 주지 않으며 기록에서는 `***`로 가린다. 8자 미만인 값은 가려지지 않는다.
- `conv`: 챗플로우의 대화 변수. `{{ conv.topic }}`으로 읽는다.

값은 글, 숫자, 참·거짓, 객체, 배열, 파일 중 하나이고 비어 있으면 null이다. 글 칸에 넣으면 모두 글자가 되고 객체와 배열은 한 줄 JSON이 된다. 변수 칸이 기대한 타입과 다르면 숫자·참거짓→글, 숫자 모양의 글→숫자, 값 하나→한 개짜리 배열만 알아서 바꾸고 나머지는 `type_mismatch`로 실패한다. 텍스트 칸은 Jinja2 문법이라 `{% if %}`, `{% for %}`와 필터가 되고, 기본 필터에 `tojson`, `fromjson`, `regex_replace`, `truncate_tokens`가 더해져 있다. 변수 값 안에 `{{ }}`가 들어 있어도 템플릿으로 풀리지 않고 글자 그대로 들어간다. 없는 변수는 빈 글이 되고 노드 기록에 경고가 남는다. '템플릿' 노드만 예외로 '변수'에 적은 이름을 `{{ q }}`처럼 바로 쓴다.

'조건 분기'는 케이스를 위에서부터 보고 처음 맞는 케이스의 가지로, 하나도 안 맞으면 '그 외' 가지로 보낸다. 연산자는 '같음', '다름', '포함', '포함 안 함', '로 시작', '로 끝남', '비어 있음', '비어 있지 않음', '보다 큼', '보다 작음', '이상', '이하', '목록에 있음', '목록에 없음', '정규식에 맞음'이고, 변수 타입에 맞지 않는 연산자는 검증 오류다. '질문 분류'는 클래스마다 가지가 있다. 타지 않은 가지의 노드는 실행되지 않고 '건너뜀'으로 표시되며, 다른 길로 들어오는 연결이 없으면 그 뒤의 노드도 건너뛴다. 두 가지가 한 노드로 다시 합쳐지면 그 노드는 한 번만 돈다. 건너뛴 노드의 변수는 비어 있는(null) 값으로 읽히므로, 갈라졌다 합쳐진 결과를 쓰려면 '변수 모으기'에 후보를 나열해 실행된 첫 값을 고른다.

서로 의존하지 않는 가지는 동시에 돈다. 한 런에서 동시에 도는 노드는 4개까지이고(`WF_MAX_PARALLEL_NODES`) '코드'와 '문서 추출' 노드는 그중에서도 각각 한 번에 하나만 돈다. '끝' 노드에 닿아도 다른 가지는 끝까지 돌고, 더 돌 노드가 없을 때 런이 끝난다.

'반복'은 배열 변수 하나를 받아 원소마다 틀 안쪽 노드를 실행한다. 틀 안에는 새 노드를 끌어다 놓는다. 이미 있는 노드를 틀 안으로 옮기는 기능은 없고, 틀 안의 노드를 틀 밖으로 끌어낼 수도 없다. 틀 안의 '반복 시작' 노드가 `item`(원소)과 `index`(순번)를 주고, 안쪽과 바깥 노드는 서로 이을 수 없다. '모을 출력'으로 고른 안쪽 노드의 출력이 원소마다 모여 입력 순서대로 `output` 배열이 된다. 기본은 한 원소씩 차례로 돌고 '병렬 실행'을 켜면 최대 4개씩 돈다. 원소는 1,000개까지이고 반복과 루프는 서로의 안에 둘 수 없다.

'반복'이 배열의 원소 수만큼 도는 것과 달리 '루프'는 '종료 조건'이 맞을 때까지 돈다. 앞 회차에서 바뀐 반복 변수를 다음 회차가 읽는다. 틀 안에 노드를 놓는 방법과 제약은 '반복'과 같다. '반복 변수'는 이름, 타입, 처음 값(고정값이나 변수)을 적어 만들고, 안쪽 노드는 `{{ loop_1.count }}`처럼 읽는다. 값을 바꾸려면 틀 안에 '변수 쓰기' 노드를 놓고 '대상 변수'에서 반복 변수를 고른다. 몇 번째 회차인지는 틀 안의 '루프 시작' 노드가 `{{ loop_start_1.index }}`로 주며 0부터 센다. '종료 조건'은 회차가 하나 끝날 때마다 보고, 반복 변수와 안쪽 노드의 출력을 읽을 수 있다. 맞으면 거기서 멈춘다. 조건은 회차가 끝난 뒤에 보기 때문에 적어도 한 번은 돈다. 조건을 두지 않으면 '최대 반복 수'(1~100, 새 노드는 10)만큼 돌고, 조건이 맞기 전에 최대 반복 수에 닿으면 경고를 남기고 정상으로 끝난다. 출력은 반복 변수마다 마지막 값과 돈 횟수 `loop_count`다. 안쪽 노드가 실패하면 루프도 그 오류로 실패한다.

저장 단추는 없다. 고치고 1.5초가 지나면 초안이 자동으로 저장되고, Ctrl+S나 위쪽 띠의 저장 상태 배지를 누르면 바로 저장한다. 배지는 '저장됨', '저장 대기', '저장 중…', '저장 실패', '저장 멈춤', '고칠 값 있음' 중 하나다. '저장 멈춤'은 다른 탭에서 같은 워크플로우를 먼저 고쳐 저장했다는 뜻이다. 이때는 '다시 불러오기'로 최신 초안을 받아야 하고 이 탭에서 저장하지 못한 변경은 사라진다. '고칠 값 있음'은 '변수'나 '설정' 탭의 입력에 잘못된 값이 있어 그 부분을 저장하지 않았다는 뜻이다. 화면을 떠나려 하면 먼저 저장을 해 보고, 실패했을 때만 확인 창이 뜬다.

저장할 때마다 서버가 그래프를 다시 검증하고 결과가 위쪽 띠에 '문제 없음'이나 '오류 2 · 경고 1'로 나온다. 누르면 '검증 결과' 목록이 열리고 항목을 누르면 그 노드가 골라진다. 목록의 '지금 다시 검증'은 저장 없이 다시 검사한다. 오류가 있어도 초안은 저장되지만 실행과 발행은 막힌다. 시작 노드가 정확히 하나인지, 워크플로우에는 끝 노드가 있고 챗플로우에는 답변 노드가 있는지, 모든 노드가 시작에서 닿는지, 순환이 없는지, 변수 참조가 앞 노드의 실제 출력을 가리키는지와 타입이 맞는지를 본다. 한도는 노드 100개, 연결 300개, 글자 칸 하나 64KB, 그래프 전체 2MB다.

'변수' 탭에는 환경 변수가 있고, 챗플로우에는 대화 변수 칸이 더 있다. 환경 변수는 이름(영문자·숫자·밑줄, 숫자로 시작할 수 없음)과 값을 넣고 '비밀'을 켜면 암호화해 저장한다. 비밀 값을 저장하려면 `.env`에 `ENCRYPTION_KEY`가 있어야 한다. '설정' 탭에는 '기본 정보'(아이콘, 이름, 슬러그, 설명. 따로 '기본 정보 저장'을 누른다), '한도', 'agent 노드 승인', '출력에서 비밀 값 가리기'(기본 켜짐), 웹앱에 보일 '웹앱 화면'(제목, 설명, 시작 문구, 추천 질문)이 있다. '최대 실행 시간(초)'은 기본 1800(60~7200)이고 입력을 기다린 시간은 빼고 센다. '런당 토큰 예산'은 기본 2,000,000이고 에이전트 노드의 자식 런까지 합치며, '런당 비용 상한(USD)'은 모델 가격을 넣어 둔 경우에만 적용된다. 환경 변수와 한도·승인·마스킹·웹앱 화면 글은 초안에 들어가 자동 저장되고 발행할 때 버전에 고정된다.

## 워크플로우 실행과 실행 기록

위쪽 띠의 '실행'을 누르면 오른쪽 패널의 '실행' 탭이 열린다. 맨 위 '입력'에 시작 노드의 필드로 만든 폼이 있다. 필수 칸을 비우면 '필수 입력입니다.'가 뜨고, 파일 칸은 '파일 고르기'로 고르는 즉시 올라간다(파일 하나에 100MB까지). 입력 필드가 하나도 없으면 위쪽 띠의 '실행'이 바로 돌린다. 탭 안의 '실행'을 누르면 먼저 초안을 저장하고(못 하면 '초안을 저장하지 못해 실행하지 않았습니다.'), 검증 오류가 있으면 시작하지 않는다. 이 실행은 저장된 초안으로 돌고 발행 버전과 상관없다.

돌기 시작하면 폼이 잠기고 '중지'가 나오며, 옆의 '이 런의 기록' 링크가 그 런의 기록 화면으로 이어진다. 아래 상태 한 줄에는 런 상태('대기열 2번째', '실행 중', '입력 기다리는 중', '완료', '실패', '중지됨'), 끝난 노드 수('노드 3개 끝남'), 지금 도는 노드, 토큰, 경과 시간이 나온다. 워크플로우 런은 한 번에 하나씩 돌고, 에이전트의 채팅 런과는 줄이 따로라 서로를 기다리지 않는다(에이전트 노드가 만든 자식 런만 에이전트 줄에서 채팅 런 뒤에 선다). 성공하면 '결과'가 나온다. 글은 마크다운으로, 객체는 펼칠 수 있는 JSON으로, 파일은 이름과 크기로 보이고 값마다 복사 단추가 있다. 실패하면 '런 실패: 오류 코드'와 메시지가 뜨고 어느 노드에서 났는지가 앞에 붙는다. 결과 파일은 이름과 크기 옆의 링크로 내려받는다(편집기에서 돌린 런도 같다). 파일을 받으려면 발행한 웹앱에서 돌리고 웹앱의 '내 실행 기록'에서 받는다.

같은 탭 아래 '노드'에 노드 런 카드가 도는 순서대로 쌓인다. 한 줄에 아이콘, 제목, 노드 id, 토큰, 걸린 시간, 상태('실행 중', '입력 대기', '성공', '실패', '건너뜀', '중지됨')가 있다. 분기 노드에는 '간 가지: …', 다시 시도한 노드에는 'N번째 시도', 에이전트 줄에서 기다리는 에이전트 노드에는 '에이전트 대기열 N번째'가 붙는다. 카드를 펼치면 오류와 경고, LLM이 쓰는 중인 글('생성 중인 글'), '입력', '출력', '처리 정보'(모델 id, HTTP 상태, 코드 종료 코드 같은 노드별 요약)가 나온다. 입력과 출력은 펼칠 때 서버에서 받아 오고, 노드 런 하나에는 각각 64KB까지(반복 안쪽은 8KB) 저장되어 넘으면 잘렸다고 표시한다. 반복은 회차별로 묶여 접히고 '실패 1' 같은 요약이 붙는다. 루프도 '1회차', '2회차'로 접히고 머리에 'N회 · 최대 M회'가 보인다. 캔버스 카드에도 실행 상태 점과 걸린 시간이 붙고, 점을 누르면 이 패널에서 그 노드 런이 펼쳐진다.

에이전트 노드가 부른 에이전트가 승인이나 질문을 요구하면 런 상태가 '입력 기다리는 중'이 되고, 그 노드 카드 안에 자식 런의 대화와 승인 카드가 뜬다('<노드> 노드의 에이전트가 실행 승인을 요청합니다'). 카드의 내용과 판단 기준은 에이전트 미리보기의 승인 카드와 같고, 승인하면 같은 런이 이어서 돈다. 거절해도 자식은 계속 돌고 그 결과가 노드 출력이 된다. '이 과업에서는 묻지 않기'를 켜면 그 자식 런의 남은 도구 호출은 묻지 않는다. 나란히 도는 가지의 에이전트 노드 둘이 함께 멈추면 승인은 한 번에 하나씩 받는다. 24시간(`WAITING_INPUT_TTL_HOURS`) 안에 답이 없으면 자식이 취소되고 그 노드의 오류 처리를 따르며, 기본은 런이 `input_timeout`으로 실패하는 것이다. 편집기를 새로 고치면 진행 중이던 런에 다시 붙지 않으니 실행 기록의 런 상세로 가서 이어 받는다. 사람 없이 돌릴 워크플로우는 '설정' 탭의 'agent 노드 승인'을 '모두 자동 승인'으로 바꾸면 되는데, 모델이 만든 명령이 이 PC에서 바로 실행되므로 믿을 수 있는 입력에만 쓴다.

'사람 입력' 노드에 닿으면 런이 멈추고 상태가 '입력 기다리는 중'이 되며, '<노드 이름> 노드가 입력을 기다립니다' 카드가 뜬다. 노드 카드의 상태는 '입력 대기'다. 카드에는 안내문과 폼 필드가 있고, 채워서 '보내기'를 누르면 '보냈습니다. 같은 런이 이어서 돕니다.'가 보이면서 같은 런이 이어서 돈다. 필수 칸이 비었거나 숫자 칸에 숫자가 아닌 것을 넣으면 보내기 전에 '필수 입력입니다.'나 '숫자를 넣으세요.'가 칸 아래에 뜨고, 서버가 값을 거절해도 그 칸 아래에 사유가 뜬다. 파일 칸은 고르는 즉시 올라간다. 카드는 편집기의 '실행' 탭에서는 상태 줄 아래에, 챗플로우 '미리보기'의 '대화'에서는 메시지 목록 끝에 뜬다. 대화에서는 그동안 입력창이 잠기고 '중지'만 쓸 수 있다. 실행 기록의 런 상세와 웹앱(워크플로우의 폼 실행, 챗플로우 대화)에서도 같은 카드가 뜨니 어디서든 한 번만 답하면 된다. 편집기의 '실행' 탭은 새로 고치면 진행 중이던 런에 다시 붙지 않으므로 그때는 런 상세에서 답한다.

폼은 뜬 때부터 24시간(`WAITING_INPUT_TTL_HOURS`) 안에 답해야 한다. 그때까지 답이 없으면 폼이 닫히고 런이 `input_timeout`으로 실패한다. 닫는 일은 매시 도는 정리 작업이 해서 24시간이 지난 뒤 한 시간쯤 늦을 수 있고, 그 사이에 보내도 닫힌 폼으로 처리된다. 기다리는 동안 서버를 다시 띄워도 폼은 남는다. 닫힌 폼에 보내면 카드에 '응답을 기다리는 시간이 지나 폼이 닫혔습니다. 런은 input_timeout으로 끝납니다.'가 뜬다. 중지됐거나 다른 곳에서 먼저 답한 런이면 '이 런은 더 이상 입력을 기다리지 않습니다. 중지되었거나 다른 곳에서 먼저 답했습니다.'가, 런이 기다리는 것이 승인이나 질문으로 바뀌었으면 '런이 기다리는 입력이 바뀌었습니다. 새로 뜬 요청에 답하세요.'가 뜬다.

노드 하나만 돌려 볼 수도 있다. 카드에 마우스를 올리거나 카드를 고르면 재생 모양 단추('이 노드만 실행')가 나온다(시작, 반복 시작, 루프 시작 노드에는 없다). 누르면 '노드 하나 실행: 이름' 창이 열려 그 노드가 참조하는 변수마다 입력칸을 준다. 글이 아닌 칸은 JSON으로 읽히면 그 값(객체, 배열, 숫자)을 쓰고, 환경 변수는 초안 값을 쓴다. 마지막에 넣은 값은 노드마다 기억한다. 결과는 같은 '실행' 탭에 나온다. 모델 호출, 외부 요청, 에이전트 실행이 실제로 일어나고, 그 노드나 안쪽 노드에 검증 오류가 있으면 시작하지 않는다. 챗플로우는 대화 턴이 도는 동안 시작하지 않는다. 이 런은 7일 뒤 지워지고 기록 목록에는 '실행 방식'을 '노드 하나'로 고를 때만 보인다.

위쪽 띠의 '실행 기록'이나 카드 메뉴의 '실행 기록'으로 기록 화면(`/workflows/<id>/logs`)을 연다. 표의 열은 '시작', '런'(런 id의 끝 8자), '실행 방식'('미리보기', '웹앱', 'API', '노드 하나'), '상태'(실패하면 오류 코드가 붙는다), '노드'(노드 런 수), '토큰', '비용', '걸린 시간'이다. 필터는 '실행 방식', '상태', '기간'이고 '더 보기'로 이어 읽는다. 챗플로우에는 '런'과 '대화' 탭이 있다. '대화' 탭은 출처('미리보기', '웹앱', 'API')를 거를 수 있는 표(출처, 제목, 턴, 마지막 메시지)이고, 제목을 누르면 메시지와 턴마다의 런 링크가 나온다. '이 대화의 런만 보기'는 '런' 탭을 그 대화로 거른다.

'런' 열의 id를 누르면 런 상세(`/workflows/<id>/logs/<런 id>`)가 열린다. 머리에 상태, 실행 방식, 버전('v3' 또는 '초안') 배지와 런 id가 있고, 아래에 '만든 때', '끝난 때', '걸린 시간', '노드', '토큰', '비용'이 있다. 탭은 '노드', '입력·출력', '원본 이벤트'다. '노드'는 실행 탭과 같은 타임라인이고, '입력·출력'은 런 입력과 결과이며(결과 파일은 내려받을 수 있다), '원본 이벤트 N'은 서버가 기록한 이벤트 표다. 진행 중인 런은 처음부터 다시 받아 그리고 끝날 때까지 따라가며, 승인이나 폼을 기다리는 런이면 해당 카드와 '중지'가 있다. 에이전트 노드가 만든 자식 런은 안쪽에 열어 볼 수 있고 '과업 세션 로그 열기'로 로그의 세션까지 갈 수 있다. 런 요약의 토큰과 비용은 LLM·질문 분류·파라미터 추출 노드가 쓴 것의 합이다. 에이전트 노드의 자식 런 사용량은 그 노드 카드에 따로 보이고 요약에는 들어가지 않는다. '설정' 탭의 '런당 토큰 예산'은 자식 런까지 합쳐서 센다.

로그(`/logs`)의 '워크플로우 런' 탭은 모든 워크플로우의 런을 시작 시각 순으로 섞어 보여 주고 '워크플로우' 필터가 하나 더 있다. '더 보기'로 50개씩 더 불러오고, 지운 워크플로우의 런도 이름 뒤에 '(삭제됨)'이 붙어 나온다. 설정 → '사용량'의 '워크플로우별'은 워크플로우마다 합산한다. 에이전트 노드가 만든 자식 런은 그 에이전트의 몫이라 '에이전트별'에서는 그 에이전트에 들어가고 '워크플로우별'에서는 '에이전트 런' 한 줄에 모인다. '에이전트별'에서는 워크플로우 런이 '워크플로우 런' 한 줄에 모인다. 어떻게 묶어도 합계는 같다.

런 이벤트(원본 이벤트 탭의 내용)는 보존 기간(기본 90일, 설정의 '워크스페이스')이 지나면 지워지고 그때 반복 안쪽 노드 런의 입력·출력도 비워진다. 런과 노드 런의 요약은 남고, 이벤트가 없는 런은 그 요약으로 그린다. 출력 파일은 런이 끝난 지 90일 뒤에 지워진다.

## 챗플로우

챗플로우는 워크플로우와 같은 편집기를 쓰되 결과를 '끝' 노드 대신 '답변' 노드로 보낸다. 사용자가 보낸 메시지는 `sys.query`로, 붙인 파일은 `sys.files`로 들어오고 메시지 하나마다 그래프가 한 번 돌아 런이 하나 생긴다. 대화와 메시지는 에이전트의 세션과 따로 저장되고 로그도 따로 본다.

위쪽 띠의 '미리보기'를 누르면 오른쪽 패널의 '미리보기' 탭(워크플로우의 '실행' 탭 자리)이 열린다. 맨 위에 '미리보기 대화' 선택 칸(제목과 '시각 · N턴'), '새 대화' 단추, 점 세 개 '대화 메뉴'('이름 바꾸기', '이 대화의 실행 기록', '대화 지우기')가 있다. 대화를 지우면 도는 런은 멈추고 붙인 파일은 지워지지만 메시지와 런은 실행 기록에 남는다. 이 브라우저는 워크플로우마다 마지막으로 연 대화를 기억해서 새로 고쳐도 같은 대화가 열린다. 탭은 셋이다.

'대화'는 에이전트 미리보기와 같은 채팅 화면이고 상태 줄(런 상태, 끝난 노드 수, 토큰, 경과 시간)과 '초안 기준' 배지가 붙는다. 미리보기는 저장된 초안으로 돌고, 메시지를 보내기 전에 초안을 먼저 저장한다. 시작 노드에 입력 필드가 있으면 첫 메시지 전에 '대화 입력' 폼이 뜬다. 값은 첫 메시지와 함께 가고 다음 메시지부터는 같은 값이 다시 쓰인다. 첫 메시지 전에는 설정 탭에서 정한 시작 문구와 추천 질문 칩이 나오고, 칩을 누르면 그 질문이 바로 전송된다. 파일은 입력창에서 붙이고 Enter로 보내며, 도는 동안은 '중지'가 나온다. '실행 과정'은 이번 턴의 노드 타임라인이고, '대화 변수'는 이 대화의 대화 변수 현재 값이다('다시 읽기'로 새로 읽는다).

'LLM' 노드의 '대화 기억'을 켜면 이 대화의 앞 턴이 시스템 글 다음에 프롬프트로 들어간다. '최근 턴 수'(1~50, 기본 10)만큼의 사용자 메시지와 답이 쌓인 순서대로 들어가고 성공한 턴만 센다. 컨텍스트를 넘으면 창을 반으로 줄여 한 번 더 시도한다. 워크플로우에서는 쓰지 않는다.

대화 변수는 '변수' 탭의 '대화 변수'에서 이름, 타입, 기본값을 정한다. 노드에서는 `{{ conv.이름 }}`으로 읽고 '변수 쓰기' 노드로 바꾼다. 바뀐 값은 그 턴이 성공으로 끝났을 때 대화에 저장되어 다음 메시지에서 보인다. 실패하거나 중지된 턴에서 바꾼 값은 저장하지 않는다.

답변은 보통 '답변' 노드의 차례가 됐을 때 글 전체가 한 번에 나간다. 아래 조건을 모두 채우면 LLM이 쓰는 글이 끝나기 전부터 흘러나온다.

- 답변 칸이 일반 글과 `{{ llm_1.text }}` 꼴의 참조로만 되어 있다. 필터나 `{% %}` 문법이 있으면 안 된다.
- 그 LLM이 'JSON 응답'을 쓰지 않고, 재시도가 0이고, 오류 처리가 '런을 실패로 끝냄'이다.
- LLM에서 답변 노드까지 사이에 '조건 분기', '질문 분류', '실패 가지' 같은 분기가 없다.

흘려보낸 글은 되돌릴 수 없어서 분기 뒤의 답변은 가지가 정해진 뒤에 한 번에 나간다. 조건을 채운 답변 노드의 카드에는 '스트리밍 가능' 배지가 붙는다. 답변 노드가 여럿이면 끝난 순서대로 이어 붙고, 다른 답변 노드가 끝나지 않았으면 순서가 섞이지 않게 기다린다. 워크플로우에는 답변 노드가 없어 결과가 끝 노드 출력으로 한 번에 나오고, 실행 탭의 타임라인에서 LLM의 '생성 중인 글'만 미리 보인다.

챗플로우 안의 에이전트 노드가 승인이나 질문에서 멈추면 대화 안에 노드 이름이 붙은 승인 카드가 뜨고 런 상태는 '입력 기다리는 중'이 된다. 입력창이 잠기고 '중지'만 쓸 수 있다. API로 보내면 409 `run_in_progress`로 거절된다. 새로 고쳐도 같은 대화를 열고 기다리는 런에 다시 붙어 카드가 돌아온다. 승인하면 같은 런이 이어서 돌고 답은 한 번만 채워진다. 다른 대화로 넘어가도 기다리는 런은 멈추지 않는다. '사람 입력' 노드의 폼도 같은 방식으로 대화 끝에 카드로 뜨고 같은 규칙을 따른다.

## 워크플로우 발행과 밖에서 쓰기

'발행' 탭(위쪽 띠의 '발행'이 같은 탭을 연다)에서 '변경 메모'(선택)를 적고 '발행'을 누르면 저장된 초안이 번호 붙은 버전(v1, v2…)으로 굳는다. 그래프, 환경 변수, 대화 변수, 설정 탭의 한도·승인·마스킹·웹앱 화면 글이 함께 고정되고 초안은 그대로 남아 계속 고칠 수 있다. 에이전트와 달리 작업공간 스냅샷은 없다. 발행 전에 초안을 먼저 저장하고, 검증 오류가 있으면 '검증 오류가 있어 발행하지 못했습니다. 빨간 표시가 있는 노드를 고치세요.'가 뜬다. '발행 이력'에는 버전, 메모, 시각이 나오고 지금 쓰는 버전에 '현재 발행'이 붙는다. '이 버전으로 되돌리기'는 그 버전을 현재 발행 버전으로 정하고 초안은 바꾸지 않는다. 챗플로우의 웹앱·API 대화는 만들 때의 버전으로 이어지고 새 대화부터 되돌린 버전을 쓴다.

웹앱은 'API' 탭 맨 위 '웹앱' 패널에서 '웹앱으로 공개'를 켜면 열린다. 발행하기 전에는 켤 수 없고('발행한 뒤에 웹앱으로 공개할 수 있습니다.') 기본은 꺼져 있다. 켜면 `http://127.0.0.1:8500/flows/<슬러그>` 주소와 '링크 복사', '웹앱 열기'가 나오고, 끄면 그 주소는 404가 된다. 웹앱도 같은 계정으로 로그인해야 열린다. 위쪽의 제목과 설명은 설정 탭의 '웹앱 화면'에서 정한 것이고, 비워 두면 워크플로우 이름과 설명이 나온다.

워크플로우 웹앱은 가운데에 시작 노드의 입력 폼이 있고 '실행'과 '중지'를 누른다. 아래로 상태 한 줄, 기다릴 때만 뜨는 승인·폼 카드, '진행'(노드가 한 줄씩 지나가고 LLM이 쓰는 글이 미리 보인다), '결과'(마크다운, JSON, 파일 내려받기 링크)가 이어진다. 오른쪽 '내 실행 기록'은 웹앱에서 돌린 런만 모으고, 누르면 그 결과를 다시 보며 '새 실행'으로 폼에 돌아온다. 고른 런은 주소의 `?run=`에 남아 새로 고쳐도 이어진다. 챗플로우 웹앱은 에이전트 웹앱과 같은 모양이다. 왼쪽에 '새 대화'와 대화 목록(점 세 개 메뉴의 '이름 바꾸기', '대화 지우기'), '콘솔로 돌아가기'가 있고 대화 주소는 `/flows/<슬러그>/c/<대화 id>`다. 위쪽에 제목과 버전 배지가 있고, 가운데 채팅은 편집기 미리보기의 '대화'와 같아서 시작 노드의 입력 폼, 시작 문구, 추천 질문, 승인·폼 카드가 같은 자리에 나온다. 다시 발행한 뒤 예전 대화를 열면 '이전 발행 버전' 배지가 붙고 그 대화는 만들 때의 버전으로 이어진다.

'API' 탭의 'API 키' 패널은 에이전트와 같다. '키 만들기'로 이름을 넣으면 키 원문이 한 번만 보이고, '폐기'하면 그 키로 오는 호출은 바로 401을 받으며, 키당 분당 60회로 제한된다. 키는 대상이 셋이고 어디서 만들었느냐로 정해진다.

| 키 | 만드는 곳 | 부르는 경로(`/api/v1/` 아래) |
|---|---|---|
| 에이전트 키 | 에이전트 빌더 | 앞 장에서 쓴 그대로: `chat-messages`, `agent-tasks`, `conversations`, `messages`, `files`, `info`, `parameters` |
| 챗플로우 키 | 챗플로우 편집기 | 같은 `chat-messages`(`/stop`, `/input`, `/events` 포함)에 같은 본문으로 보내면 챗플로우가 돈다. 받는 이벤트 이름만 `workflow.*`·`node.*`·`answer.*`로 다르다. `conversations`, `messages`, `files`, `info`, `parameters`와 런 조회·중지·응답(`workflows/run/<id>`), `workflows/logs`도 쓴다 |
| 워크플로우 키 | 워크플로우 편집기 | `workflows/run`, `workflows/run/<id>`(조회), `workflows/run/<id>/stop`, `workflows/run/<id>/input`, `workflows/logs`, `files`, `info`, `parameters` |

경로가 받지 않는 대상의 키로 부르면 400 `wrong_target`이 오고 안내는 "이 경로는 워크플로우 API 키로 부른다. 이 키는 에이전트에 묶여 있다" 꼴이다. 키는 만든 워크플로우의 발행 버전만 부를 수 있고, 그 키로 만든 런·대화·파일만 볼 수 있다. 발행 전에 `workflows/run`을 부르면 409(`workflow_not_published`), 입력이 시작 노드의 필드에 맞지 않으면 422(`invalid_inputs`)다. 호출하는 쪽을 가르는 `user` 이름표는 에이전트 API와 같다. `GET /api/v1/info`는 키가 가리키는 워크플로우의 이름·종류·발행 여부를, `GET /api/v1/parameters`는 발행 버전의 입력 필드를 알려 준다.

'API' 탭 아래 '호출 예시'에는 워크플로우용 세 개(실행 스트리밍, 실행 기다리기, 실행 상태)와 챗플로우용 네 개(메시지 스트리밍, 메시지 기다리기, 대화 목록, 대화 메시지)가 있고, `inputs`는 시작 노드의 필드 이름으로 채워져 있다. Git Bash에서 `API_KEY=발급한_키`를 먼저 넣고 실행한다. 워크플로우는 이렇게 부른다.

```bash
curl http://127.0.0.1:8500/api/v1/workflows/run \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @- <<'JSON'
{"inputs":{"q":"안녕"},"user":"me","response_mode":"blocking"}
JSON
```

`response_mode`를 빼면 `streaming`이라 SSE로 노드 이벤트가 흘러오고(`curl -N`), 첫 이벤트는 `workflow.queued`, 마지막은 `workflow.completed`다. `blocking` 응답에는 `workflow_run_id`, `status`, `outputs`(끝 노드들이 모은 값, 성공이 아니면 null), `usage`, `elapsed_ms`가 있고 실패하면 `error`가 채워진다. 파일 입력은 `POST /api/v1/files/upload`(multipart)로 올리고 받은 `file_id`를 시작 노드의 파일 필드 값으로 넣는다. 챗플로우는 `chat-messages`로 부르고 본문은 에이전트와 같다.

```bash
curl http://127.0.0.1:8500/api/v1/chat-messages \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @- <<'JSON'
{"query":"안녕하세요","inputs":{},"user":"me","response_mode":"blocking"}
JSON
```

응답에는 `conversation_id`, `message_id`, `run_id`, `answer`, `usage`, `status`가 있다. `conversation_id`를 다음 요청에 같이 보내면 같은 대화가 이어지고, `inputs`를 비우면 앞 메시지의 입력이 다시 쓰인다. 끝나지 않은 런이 있는 대화에 보내면 409(`run_in_progress`)다. 대화 목록은 `GET /api/v1/conversations?user=me&limit=20`, 메시지는 `GET /api/v1/messages?conversation_id=<id>&user=me`로 본다.

에이전트 노드가 승인이나 질문에서 멈추면 응답이 `"status":"waiting_input"`으로 끝나고 `pending_interaction`에 어느 노드(`node_id`)가 무엇을 묻는지 담긴다. 워크플로우 키는 `POST /api/v1/workflows/run/<워크플로우 런 id>/input`, 챗플로우 키는 `POST /api/v1/chat-messages/<런 id>/input`에 `{"decision":"approve"}`(질문이면 `{"answer":"…"}`)를 보내면 같은 런이 이어서 돈다. `response_mode`를 주지 않으면 202로 바로 돌아오니 `GET /api/v1/workflows/run/<런 id>`로 상태를 본다. 답은 24시간 안에 해야 하고, 런을 멈출 때는 같은 경로의 `/stop`을 쓴다. 사람 없이 돌릴 워크플로우는 설정 탭에서 'agent 노드 승인'을 '모두 자동 승인'으로 하는데, 위험을 알고 하는 선택이다.

'사람 입력' 노드에서 멈출 때도 응답이 `"status":"waiting_input"`으로 끝난다. 이때 `pending_interaction`의 `kind`가 `form`이고 `form`에 안내문(`description`)과 입력 칸(`fields`)이 담긴다. 같은 `/input` 경로에 `kind`를 `form`으로 하고 칸 이름을 키로 한 `values`를 보낸다.

```bash
curl http://127.0.0.1:8500/api/v1/workflows/run/<워크플로우 런 id>/input \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  --data-binary @- <<'JSON'
{"kind":"form","values":{"reply":"승인합니다"},"user":"me","response_mode":"blocking"}
JSON
```

챗플로우 키는 `POST /api/v1/chat-messages/<런 id>/input`에 같은 본문을 보낸다. 파일 칸의 값은 `POST /api/v1/files/upload`로 올려 받은 `file_id`이고, 파일 여러 개는 그 배열이다. 값이 틀리면 422(`invalid_inputs`)이고 `error.details`에 칸별 사유가 담긴다. 이미 답했거나 중지된 런이면 409(`run_not_waiting`), 승인·질문을 기다리는 런에 폼을 보내거나 폼을 기다리는 런에 `decision`·`answer`를 보내면 409(`wrong_input_kind`), 24시간이 지났으면 409(`input_timeout`)다. 폼은 '모두 자동 승인'으로 건너뛰지 않으니, 사람이 없는 환경에서는 이 호출을 스크립트가 대신 보내야 런이 끝난다.

## DSL 내보내기·가져오기

워크플로우는 YAML 파일 하나로 내보내고 다시 가져올 수 있다. 다른 워크스페이스나 PC로 옮기거나 백업 삼아 쓴다. 파일에는 이름·아이콘·설명, 환경 변수와 대화 변수, 설정, 그래프(노드와 연결)가 들어 있고 `dsl_version: 1`로 시작한다.

내보내기는 편집기 위쪽 띠의 'DSL' 메뉴에서 'YAML로 내보내기'를 고른다. 'DSL 내보내기' 창에서 '버전'(초안, 현재 발행 버전, 지난 버전)을 고르고 '내려받기'를 누르면 `<워크플로우 이름>.yml`이 받아진다. 초안은 먼저 저장한 뒤 내보낸다. '비밀 값 포함'은 꺼져 있고, 끈 채로 내보내면 비밀 환경 변수는 이름만 들어간다. 켜면 '비밀 환경 변수 값이 평문으로 파일에 들어갑니다.' 경고가 뜨고, 받은 뒤에도 '안전한 곳에만 두세요.'라는 알림이 나온다. 그 파일은 `.env`처럼 다루고 저장소나 채팅에 올리지 않는다. 에이전트 노드는 에이전트의 id가 PC마다 달라서 슬러그가 같이 적히고, 가져올 때 같은 슬러그의 에이전트를 찾아 이어 준다. 없으면 노드는 남고 검증 오류(`agent_not_found`)가 되니 에이전트를 다시 고른다.

가져오기는 두 곳에서 한다. 목록의 '가져오기'는 새 워크플로우를 만든다. 'DSL 가져오기' 창의 '파일' 탭에서 .yaml·.yml 파일(2MB까지)을 고르거나 '붙여 넣기' 탭에 YAML을 붙여 넣고 '가져오기'를 누른다. 결과 창에 출처('우리 DSL' 또는 'Dify DSL에서 변환'), 노드 수, '옮기지 못한 노드', '바꾸거나 버린 것', '검증 결과'가 나오고 '편집기 열기'로 바로 간다. 편집기의 'DSL' 메뉴에 있는 '가져와서 이 초안 덮어쓰기'는 지금 워크플로우의 초안을 파일 내용으로 바꾼다. 확인 창을 거치고 되돌릴 수 없다. 발행 버전과 이름·아이콘·설명은 그대로이고 같은 종류의 파일만 받는다. 값 없이 들어온 환경 변수는 저장돼 있던 값을 남긴다. 파일이 거부되는 경우는 2MB 초과, 읽을 수 없는 YAML(어느 행·열인지 나온다), 우리 것도 Dify 것도 아닌 형식, 서버보다 새로운 DSL·노드 버전, 워크플로우·챗플로우가 아닌 Dify 앱, 너무 큰 그래프, 덮어쓸 파일과 종류가 다른 경우이고 이유가 문장으로 나온다.

Dify에서 내보낸 YAML도 일부는 가져온다. 워크플로우 앱은 워크플로우로, 챗플로우(advanced-chat) 앱은 챗플로우로 들어온다. 옮기는 노드는 시작, 끝, 답변, LLM, 코드(파이썬만), HTTP 요청, 조건 분기, 반복, 루프, 템플릿, 변수 모으기, 변수 쓰기, 질문 분류, 파라미터 추출, 리스트 연산, 문서 추출, 도구, 사람 입력이다. 도구는 현재 시각, JSON 읽기, 정규식 추출, 웹 페이지 가져오기에 해당하는 Dify 도구만 옮기고, 사람 입력은 버튼이 하나인 폼만 옮긴다. 그 밖의 노드(예: 지식 검색, Dify의 에이전트), 자바스크립트 코드 노드, 맞는 내장 도구가 없는 도구, 버튼마다 가지가 갈라지는 사람 입력은 '옮기지 못한 노드'로 남는다. 자리와 연결은 그대로 들어오고 검증 오류가 되어 실행과 발행이 막히니, 지원하는 노드로 바꿔 끼우거나 지운다. 옮기면서 바뀌는 것도 있다. 변수 참조는 `{{#node.var#}}`에서 `{{ node.var }}`로 바뀌고 숫자 id는 `n<id>`가 된다. 모델은 모두 Gemini 폴백 목록의 첫 모델로 바뀐다. HTTP 노드의 form-data 본문은 urlencoded로 바뀌고 Basic·사용자 지정 인증은 헤더 인증으로 바뀐다. 조건 분기의 비교 값 안에 든 변수 참조는 옮기지 못하고 글자로 남는다. 루프의 최대 반복 수는 100을 넘으면 100으로 줄고, 사람 입력의 전달 방법과 대기 시간 설정은 가져오지 않는다. 캔버스 메모와 플러그인 의존성은 가져오지 않는다. 시작 문구와 추천 질문은 '웹앱 화면'으로, 파일 업로드 기능은 시작 노드의 `files` 입력으로 들어온다. 비밀 환경 변수는 Dify도 값을 내보내지 않으니 이름만 들어오고, 가져온 뒤 '변수' 탭에서 값을 다시 넣는다. 무엇이 바뀌었는지는 결과 창의 '바꾸거나 버린 것'에 나온다.

어느 파일이든 그 안의 코드 노드는 믿지 않는다. 가져온 코드 노드에는 카드에 '가져온 코드' 배지가 붙고, 노드의 코드 폼에 '가져온 코드입니다' 안내가 뜬다. 코드를 끝까지 읽고 '검토 완료'를 눌러야 배지가 사라지고 실행과 발행이 풀린다. 그 전에는 검증 오류(`imported_code_unreviewed`)가 막는다. 코드는 승인 없이 이 PC의 샌드박스에서 돌기 때문이다. 파일의 승인 모드가 '모두 자동 승인'이어도 '에이전트 발행 버전 설정대로'로 낮춰 들어오고 '바꾸거나 버린 것'에 그렇게 나온다. 필요하면 설정 탭에서 다시 켠다.

## 지휘자 에이전트

지휘자는 따로 있는 종류가 아니다. 에이전트 빌더의 '도구와 스킬' 탭에서 다른 에이전트를 '하위 에이전트'로 하나 이상 고른 보통의 에이전트다. 모델이 `call_agent` 도구로 하위 에이전트에게 과업을 맡기고, 결과를 받아 이어서 일한다. 워크플로우의 에이전트 노드가 정해 둔 순서로 에이전트를 부른다면, 지휘자는 모델이 대화 중에 누구에게 맡길지 정한다.

'하위 에이전트' 패널에는 같은 워크스페이스의 다른 에이전트(자기 자신과 지운 것은 빠진다)가 이름, 설명 한 줄, 'v2 발행' 또는 '초안만' 표시와 함께 나온다. 체크하면 하위 에이전트가 되고 10개('n/10개 선택')까지 고른다. 모델은 각 에이전트의 설명을 보고 누구에게 맡길지 정하니, 설명이 비어 있으면 '설명 없음' 경고가, 발행하지 않았으면 '미발행' 경고가 붙는다. 저장하면 '하위 에이전트 경고 N건'이 뜬다. 항목마다 '호출 설정'이 있다. '결과 형식'은 '글'(하위 에이전트의 마지막 답과 결과 파일, 기본)이나 'JSON'이다. 'JSON'은 출력 스키마에 맞춘 값을 받는 대신 그 값을 내는 단계가 더해져 스텝과 토큰을 더 쓴다. 스키마는 '여기서 정한 스키마'로 고정하거나 '모델이 호출 때 정함'으로 둔다. '결과 파일을 지휘자 작업공간으로 복사'는 기본이 켜져 있고, 끄면 결과에 파일 목록만 적히고 파일은 하위 에이전트 세션에만 남는다. '승인'을 '끄기'로 하면 이 호출에서 하위 에이전트의 도구를 묻지 않고 실행한다.

저장과 발행에서 걸리는 것이 있다. 자기 자신이나 순환(A가 B를, B가 A를 고른 것)은 저장이 막힌다. 발행하지 않은 하위 에이전트가 있으면 지휘자도 발행하지 못하고 "하위 에이전트 <이름>을(를) 먼저 발행한다"가 나온다. 사슬이 호출 깊이 한도보다 길면 경고만 뜬다. '승인과 한도' 탭의 '하위 에이전트 호출 수'(기본 20, 0~100)는 런 하나가 `call_agent`를 부를 수 있는 횟수다. 하위 에이전트가 다시 부르는 호출까지 합친 상한이고, 0이면 도구를 붙이지 않는다. 깊이는 `.env`의 `ORCHESTRATION_MAX_DEPTH`(기본 2)로 정한다. 지휘자가 0, 하위 에이전트가 1, 그 하위가 2라서 기본으로는 두 단계 아래까지 부르고, 이 깊이에 닿은 런에는 `call_agent`가 없다.

대화 안에서는 `call_agent`를 부른 자리에 '하위 에이전트 <이름>' 카드가 생긴다. 머리에 상태('부르는 중', '승인 대기', 끝나면 '완료'·'실패'·'중지됨'), 스텝 수, 경과 시간이 나온다. 발행 버전이 없는 하위 에이전트를 미리보기에서 돌리면 '초안' 배지가 붙고, 이때는 첨부 파일과 스킬만 있는 빈 작업공간에서 시작한다. 카드를 펼치면 하위 에이전트의 대화가 입력창 없이 열려 도구 카드까지 보인다. 하위 에이전트가 승인을 요구하면 그 안에 '<이름>의 승인 요청' 카드가 뜬다. 거기서 '이 대화에서는 묻지 않기'를 켜면 이 대화의 지휘자와 하위 에이전트가 이후 도구 호출을 묻지 않는다. 카드의 '중지'는 그 하위 에이전트만 멈추고, 지휘자는 '중지됨' 결과를 받아 다른 방법을 고른다. 지휘자를 중지하면 하위 에이전트와 그 아래까지 모두 멈춘다. 끝난 카드에는 '하위 에이전트 결과'로 '결과 파일' 내려받기와 'JSON 결과'가 붙는다.

하위 에이전트는 한 번에 하나씩 돈다. 한 스텝에서 여럿을 불러도 차례로 처리한다. 기다리는 동안 지휘자의 입력창은 잠기고 상태 줄에 '하위 에이전트 <이름> 실행 중'이 나온다. 하위 에이전트에게는 `ask_user` 도구가 없다. 사용자에게 직접 물을 수 없으니 확인할 것은 결과 글에 적어 돌려주고 지휘자가 대신 묻는다. 승인 카드는 그대로 뜬다. 지휘자는 `files`로 작업공간 파일을 20개까지 넘길 수 있고, 하위 에이전트의 결과 파일은 지휘자 작업공간의 `agents/<슬러그>/<런 id>/` 아래로 복사된다. 하위 에이전트는 자기 버전의 지시문·도구·한도로 돌고 사용량도 그 에이전트의 몫으로 잡혀, 설정 → '사용량'의 '에이전트별'에서 그 에이전트에 들어간다.

어느 버전을 부르는지는 지휘자가 어디서 도느냐에 달렸다. 미리보기(초안)에서는 하위 에이전트의 발행 버전이 있으면 그것을, 없으면 초안을 쓴다. 웹앱과 API로 도는 발행된 지휘자는 호출 시점의 발행 버전을 쓰고, 발행 버전이 없으면 `agent_not_published` 도구 오류가 나서 모델이 다른 방법을 고른다. 하위 에이전트를 고쳐 다시 발행하면 다음 호출부터 반영된다. API로 부를 때 `blocking` 호출은 하위 호출을 포함한 최종 답을 한 번에 돌려주고, 스트림은 하위 호출 동안 끊기지 않는다.

로그에서는 하위 에이전트의 런에 '하위' 배지가, 지휘자 런에 '하위 N개' 칩이 붙는다. 런 상세에 '하위 런 N' 탭이 있어 하위 런을 펼쳐 스텝과 도구까지 내려가고, 머리에 '하위 포함 합계'(토큰과 비용)가 나온다. 하위 런의 상세에는 '부모 런' 링크가 있고, 런 목록은 '부모 런 …의 하위 런만'으로 거를 수 있다. 하위 에이전트의 대화는 소스가 '과업'인 세션으로 남는다.

## 운영과 문제 해결

데이터는 모두 `DATA_DIR`(예: `C:\wf-data`) 아래에 있다. 안에 DB `app.db`, 파일 `storage`, 작업공간 `workspaces`, 워크플로우 런의 임시 폴더 `wf-workspaces`, pip 캐시와 문서 추출 파서를 두는 `cache`, 로그 `logs`, 허용 목록 `allowlist.txt`가 있다. `wf-workspaces`는 워크플로우 런마다 만들어지는 폴더로 code 노드의 스크립트와 큰 HTTP 응답, 문서 추출이 옮겨 온 파일이 잠깐 놓인다. 성공하거나 중지된 런의 것은 끝날 때, 실패한 런의 것은 1시간 뒤에 지워진다.

백업은 `uv run platform backup` 한 줄이고 결과는 저장소의 `backups\<시각>\`에 생긴다. 서버가 떠 있어도 되고 `--with-workspaces`를 붙이면 작업공간까지 담는다. 워크플로우 테이블과 `storage\wf-files`는 기본으로 들어가고 `wf-workspaces`와 `cache`는 들어가지 않는다. 복구는 그 폴더를 `DATA_DIR`로 쓰는 것이 전부이고, 파서는 pdf·docx를 처음 읽을 때 다시 받는다. `.env`와 `ENCRYPTION_KEY`는 백업에 들어가지 않으니 따로 보관한다. 자세한 것은 [백업과 복구](ops/backup-restore.md)에 있다.

상태 점검은 `uv run platform doctor`다. 셸, 샌드박스 파이썬과 pip, 데이터 폴더, 긴 경로 정책, 실행 정책, 포트, 서브프로세스, 암호화 키, 디스크(데이터 폴더 다섯 곳의 크기)를 `OK`와 `WARN`으로 보여 준다. 서버가 떠 있을 때는 포트 항목이 `WARN`으로 나오는 것이 정상이다.

로그 파일은 `DATA_DIR\logs\app.log`에 JSON 한 줄씩 쌓이고 콘솔에도 같은 줄이 나온다. 키와 토큰은 `***`로 가려져 기록된다. 서버 상태는 `curl -s http://127.0.0.1:8500/healthz`로 보고 `rss_mb`가 서버의 메모리다. 로그 읽는 법은 [운영](ops/operations.md#로그와-헬스)에 있다.

| 증상 | 확인할 것 |
|---|---|
| 서버가 바로 죽거나 doctor의 포트 항목이 `WARN` | 8500을 다른 프로세스가 쓰고 있다. 이전에 띄운 서버가 남았는지 `Get-NetTCPConnection -LocalPort 8500 -State Listen`으로 찾고, 다른 프로그램이면 `.env`의 `SERVER_PORT`를 바꾼다(8000, 8080은 피한다) |
| 접속하면 "화면이 아직 빌드되지 않았다"만 나온다 | `corepack pnpm --dir apps/web build`를 하고 서버를 다시 띄운다. build가 `Out of memory`로 죽으면 다른 프로그램을 닫고 build만 단독으로 돌린다 |
| 런이 모델 오류로 실패한다 | 설정의 'LLM'에서 '키 상태'를 본다. 429면 그 키는 잠시 쉬고 다음 키로, 키가 다 막히면 폴백 순서의 다음 모델로 넘어간다. 전부 막히면 `model_unavailable`로 실패하고 '잠시 뒤 다시 보내 볼 수 있습니다.'가 붙는다. 자동 재시도는 없으니 나중에 다시 보낸다. '사용 중지 (401·403)'면 키가 틀린 것이다 |
| 승인 카드가 안 뜬다 | 미리보기 위쪽 칩이 '승인 없음'인지, '자동 승인 켜짐'이 떠 있는지 본다. '승인과 한도' 탭을 고쳤으면 저장했는지도 본다. 파일 도구와 HTTP GET은 어느 모드에서도 묻지 않는다 |
| 메시지를 보냈는데 거절된다 | 승인 카드나 질문이 열려 있거나(409), 작업공간이 디스크 한도를 넘었다. 작업공간 창에서 '패키지 삭제'나 '작업공간 초기화'를 한다 |
| 메모리가 모자라다 | 서버는 보통 100MB 남짓이고 예산 300MB를 넘으면 로그에 `memory.over_budget`이 남는다. 화면 build나 테스트는 겹쳐 돌리면 죽으니 하나씩 돌린다. 에이전트가 메모리를 많이 쓰는 코드를 돌리면 작업공간 프로세스 상한에서 `MemoryError`로 실패하고 서버는 멀쩡하다 |
| code 노드가 `timeout`으로 실패한다 | 시간 제한은 기본 30초다. `.env`의 `WF_CODE_TIMEOUT_SEC`(1~60)를 바꾸거나 노드의 '시간 제한(초)'에 60초까지 적는다. 메모리 256MB, 프로세스 8개, 반환값 256KB, print 출력 1MB를 넘으면 각각 `memory_limit`, `output_too_large`, `stdout_too_large` 같은 다른 코드로 끝난다. 코드 안의 예외는 `code_error`이고 노드 기록의 '처리 정보'에 stdout·stderr(앞 32KB)와 오류 위치가 남는다 |
| 'HTTP 요청' 노드나 '도구'의 '웹 페이지 가져오기'가 `http_host_not_allowed`로 실패한다 | 호스트가 허용 목록에 없다. 두 곳은 같은 목록을 쓴다. 설정의 'HTTP 허용 목록'에 나온 파일(`allowlist.txt`)에 한 줄 더하면 몇 초 안에 반영된다. 사설·루프백 주소는 목록에 넣어도 `http_address_blocked`로 막힌다. 4xx·5xx 응답은 실패가 아니라 `status_code` 출력이다 |
| 문서 추출 노드가 `parser_install_failed`로 실패한다 | pdf·docx를 처음 읽을 때 서버가 파서(`pypdf`, `python-docx`)를 pip으로 받아 `DATA_DIR`의 `cache\wf-extract`에 둔다. 이때만 인터넷이 필요하고 수 초 걸린다. 연결이 막혔거나 `DATA_DIR` 경로가 길어서 받은 패키지의 경로가 Windows의 260자 제한에 걸리면 설치가 실패한다. 연결을 확인하거나 `DATA_DIR`을 `C:\wf-data`처럼 짧게 두고(`doctor`의 '데이터 폴더' 항목이 80자를 넘으면 `WARN`으로 알린다) 다시 실행한다. 설치가 끝난 뒤에는 인터넷 없이 읽고, `cache\wf-extract`를 지우면 다음에 다시 받는다. 파일 하나를 60초 안에 못 읽으면 `extract_timeout`, 메모리 512MB를 넘으면 `memory_limit`으로 실패한다. txt, md, csv, html은 파서가 필요 없다 |
| 서버를 다시 띄웠더니 워크플로우 런이 실패했다 | 도는 중에 서버가 꺼진 런은 `shutdown`으로 실패하고 자동으로 이어 하지 않는다. 같은 입력으로 다시 실행한다. 에이전트 노드의 승인이나 질문, '사람 입력' 노드의 폼을 기다리던 런은 그대로 남아 24시간 안에 답하면 이어진다. 초안으로 돌리던 런이 기다리는 동안 초안을 고쳤다면 `graph_changed`로 끝나니 이때도 다시 실행한다 |
| 워크플로우 런이 '입력 기다리는 중'에서 멈춰 있다 | 에이전트 노드가 승인이나 질문을 기다리거나 '사람 입력' 노드가 폼을 기다리는 것이다. 승인·질문은 노드 카드에서, 폼은 상태 줄 아래의 폼 카드에서 답하고, 편집기를 새로 고쳤다면 실행 기록의 런 상세에서 답한다. 챗플로우는 대화 안의 카드에서 답하며 그동안 새 메시지는 보낼 수 없다. 폼은 24시간 안에 답이 없으면 닫히고 런이 `input_timeout`으로 실패한다 |

안전 수칙은 이 넷이다. 근거는 [보안 확인](ops/security.md#운영-시-지킬-것)에 있다.

- `.env`(Gemini 키와 `ENCRYPTION_KEY`)는 채팅, 스크린샷, 저장소에 올리지 않고, `ENCRYPTION_KEY`는 백업과 다른 곳에 한 벌 더 둔다.
- '이 세션에서는 묻지 않기'와 '승인 없음'은 믿을 수 있는 입력일 때만 쓰고 끝나면 되돌린다. 카드에 `.env`, 작업공간 밖 경로, 처음 보는 주소가 보이면 거절한다.
- 허용 목록은 기본 PyPI와 GitHub에서 필요한 도메인만 한 줄씩 늘리고 `*`는 피한다. 서버를 방화벽이나 터널로 PC 밖에 열지 않는다.
- 남에게서 받은 DSL은 code 노드와 HTTP 요청 노드의 주소를 읽은 뒤에 쓴다. '비밀 값 포함'으로 내보낸 파일은 `.env`처럼 다룬다.

## 명령 모음

저장소 루트에서 돌린다. uv가 PATH에 없으면 `uv` 대신 `python -m uv`를 쓴다.

| 명령 | 하는 일 |
|---|---|
| `uv run platform serve` | 서버를 띄운다. `--reload`는 코드를 고치는 중에만 쓴다 |
| `uv run platform doctor` | 환경을 점검한다 |
| `uv run platform backup` | 백업한다. `--with-workspaces`, `--out <폴더>`, `--keep N` |
| `uv run platform reset-password` | 비밀번호를 다시 정한다 |
| `uv run platform migrate` | DB를 최신 스키마로 올린다. 서버가 뜰 때도 자동으로 한다 |
| `bash scripts/smoke.sh` | 떠 있는 서버의 기본 응답을 확인한다 |
| `bash scripts/smoke-api.sh <API 키>` | 에이전트 키로 서비스 API를 훑는다. 실제 모델을 몇 번 부른다 |
| `curl -s http://127.0.0.1:8500/healthz` | 서버 상태. `runner`에 에이전트·워크플로우 줄의 도는 런과 기다리는 런이 따로 나온다 |
| `python scripts/memcheck.py` | 서버를 따로 띄워 메모리를 잰다. 에이전트 런 하나와 워크플로우 런 하나를 돌린다. `uv run platform memcheck`와 같다 |
| `uv run pytest` | 서버 테스트 |
| `uv run ruff check . && uv run ruff format --check . && uv run pyright` | 린트와 타입 검사 |
| `corepack pnpm --dir apps/web build` | 화면을 빌드한다 |
| `corepack pnpm --dir apps/web dev` | 화면 개발 서버(5173) |
| `corepack pnpm --dir apps/web lint`, `typecheck`, `test`, `e2e` | 화면 검사. `e2e`는 8502에 시험용 서버를 먼저 띄운다 |

검사와 빌드는 메모리 때문에 하나가 끝난 뒤 다음을 돌린다. 순서와 이유는 [README](../README.md#개발)에 있다.
