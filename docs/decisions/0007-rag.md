# ADR-0007: 지식 베이스는 자체 구현, 색인은 app.db 옆의 sqlite-vec·FTS5 파일

- 상태: 채택(2026-11-02). 사용자가 설계서(`docs/design/phase3-rag.md`) 1절의 쟁점 Z1~Z10에 따로 답하지 않고 진행을 지시해, 각 쟁점의 "결정이 없으면" 값으로 M21a부터 진행한다. Z1은 무료로 시작하고 유료 키 자리만 만든다. Z2는 (b)다. 사용자가 나중에 다르게 정하면 이 ADR을 고친다. v2 (architect, 2026-11-02, design-reviewer 검토 반영).
- 날짜: 2026-11-02
- 배경: 1단계(에이전트 샌드박스)와 2단계(워크플로우·챗플로우)가 끝났다. 3단계는 Dify의 클래식 지식 베이스를 기능적으로 따라가는 RAG다. ADR-0001 D3~D5, ADR-0002~0006을 유지하되 ADR-0003·0004를 한 줄씩 개정한다(D8). 키 8개가 모두 무료 등급이고, 무료 등급 임베딩은 키(프로젝트)당 분당 100건이며 약관상 입력이 제품 개선에 쓰일 수 있다. 서버 RSS 예산은 300MB(2단계 끝 137MB)다. 근거는 `docs/research/rag-text2sql-2026-11.md`와 `docs/research/gemini-api-2026-10.md`에 있고 수치는 설계서가 인용한다.

## 결정

### D1. 관리형 RAG(File Search)를 쓰지 않고 직접 만든다
- File Search는 top_k·문턱·재순위·하이브리드가 없고 청크 원문을 돌려주지 않으며 데이터가 Google에 무기한 남는다. Dify 지식 기능(청크 편집, 검색 시험, 메타데이터 필터, 인용, Economical)을 복제할 수 없다. 검색 서비스에 공급자 경계만 두고 구현하지 않는다(설계 Z3).

### D2. 원문·상태는 app.db, 벡터·전문 색인은 `data/knowledge/index.db`
- app.db에 `knowledge_base`, `kb_document`, `kb_segment`, `kb_child_chunk`, 메타데이터·평가·질의 기록 테이블(마이그레이션 0007). 모든 테이블에 `workspace_id`. 문서 삭제는 소프트 삭제 뒤 레인 작업(한 요청이 쓰기 락을 오래 잡지 않게).
- index.db는 sqlite-vec 0.1.9 vec0(코사인, 브루트포스)와 FTS5 contentless 테이블을 KB마다 하나씩 두는 파생 파일이다. 64KB 페이지(WAL 전에 설정), mmap 끔, aiosqlite 직접 연결(writer 1 + reader 2), Alembic 밖(자체 `schema_version`), 백업에 포함(`--no-index`로 제외 가능).
- 파일을 나눈 이유: 페이지 크기 분리, 쓰기 잠금 분리, 긴 KNN 읽기가 app.db WAL을 키우지 않음, 확장 없는 연결이 app.db를 평소처럼 연다. 원자성이 없는 대가는 세그먼트의 `index_state`, 쓰기 순서, 색인 설정 비교(`config_key`·`embedding_version`), 매시 고아 정리로 메운다(설계 5.4).
- `VectorIndex`·`FtsIndex` 프로토콜 뒤에 두어 sqlite-vec(pre-1.0)를 바꿔 끼울 수 있게 한다. upsert는 DELETE+INSERT.

### D3. 임베딩은 `gemini-embedding-2` 768차원 접두어, OpenAI 호환 경로, 총량은 리미터가 묶는다
- 새 KB 기본값은 `gemini-embedding-2`, 768차원, 문서·질의 접두어다. 모델·차원·접두어·task type은 KB의 색인 설정으로 저장하고 바꾸면 전량 재임베딩한다. `EmbeddingClient`(`app/llm/embeddings.py`)는 채팅 어댑터의 `KeyPool`·SDK 클라이언트·오류 분류를 같이 쓰고 전송만 프로토콜로 나눈다. 네이티브 클라이언트는 만들지 않는다(4단계 4-1이 만들어 전송을 더한다. 한 벌 규칙, 설계 Z8).
- 리미터는 항목 수(분당 90, 사람이 기다리는 요청 예약 10, 인제스트 80을 20초 조각으로)와 추정 토큰(기본 끔. 1,004토큰 95개 한 요청이 200이었다)의 이중 버킷이고, "지속 처리량을 프로젝트 하나의 문서화된 한도 안에 둔다"는 원칙을 실제로 보장하는 장치다. 429는 본문의 `quotaId`·`retryDelay`로 분당·일일을 가른다(설계 Z2·6.6). 상한을 넘는 입력은 API가 조용히 잘라 버리므로 우리 쪽에서 강제 분할한다. 같은 입력은 같은 벡터이므로 내용 해시 캐시를 둔다.
- 무료 등급 속도는 인제스트 몫 분당 80건과 일일 한도 하루 1,000건(실측)에 묶인다. 1만 청크는 분당으로는 약 2시간이지만 일일 한도 때문에 열흘이 걸리므로, 큰 KB는 유료 키(Z1 (b))가 전제다.

### D4. 한국어 전문 검색은 음절 bigram FTS5
- 우리 코드가 NFC → bigram 변환한 문자열을 `unicode61` FTS5 contentless 테이블에 넣고, 질의는 df 5% 초과 bigram을 뺀 OR 가방이다(KorQuAD MRR@10 0.900~0.907, Kiwi와 같다). Kiwi는 RSS +177~309MB라 쓰지 않는다. SQLite 3.43 미만이면 본문 저장 FTS5로 폴백한다. Economical 모드는 이 FTS만이다.

### D5. 하이브리드 기본은 벡터 후보 안 min-max 점수 가중합(a=0.7), 문턱은 코사인 원값
- 벡터 후보 50개 안에서 코사인을 min-max로 맞추고 bm25를 목록 최대값으로 나눠 `0.7·벡터 + 0.3·전문`으로 더한다. 합성 평가 재실측(설계 7.2 표)에서 권장 설정의 R@1이 1.000(벡터 단독 0.981)이었고 코사인 원값 가중합(0.943)과 RRF(0.981)보다 나았다. 점수 문턱은 결합 전 코사인 원값에만 걸고 기본은 끔(켜면 0.5). RRF(k=60)와 LLM 재순위(확장)는 선택지다. Top K 기본 4, 상한 20.
- 평가셋과 평가 실행(R@1·3·5, MRR@10)을 KB 화면에 넣어 사용자의 실제 문서로 기본값을 다시 잰다.

### D6. 인제스트는 세 번째 Supervisor 레인, 문서 단위 상태, 재개 가능 작업
- `knowledge_supervisor`(동시 1)가 문서 id를 키로 색인·삭제 작업을 돈다. 상태는 Dify 이름이고 진실은 `kb_document` 행이다. 재기동 복구가 진행 중 문서를 다시 넣고 끝난 유닛을 건너뛴다(임베딩은 멱등). 일시 정지는 `Supervisor.dequeue`(꺼낸 id를 건너뛰는 집합)로 한다. 진행은 2초 폴링(SSE 없음). 일일 한도 429는 자동 재투입 없이 `retry_after`와 함께 멈춘다.
- 파싱(pdf·docx)은 세 번째 `LocalWorkspaceBackend`(`data/kb-work/`)에서 2단계 `extract_runner`로 한다. 서버는 파서를 import하지 않는다. 스캔 PDF 모델 읽기는 확장 항목이다.

### D7. 쓰는 곳은 노드 2종, llm 컨텍스트, 에이전트 내장 도구, (확장) KB 단위 서비스 API 키
- `knowledge_retrieval`(출력 `result`는 Dify `RetrieverResource` 필드명, `result_text`, `count`)과 `knowledge_index`(글·파일 → KB 문서)를 2단계 레지스트리에 등록한다. 전용 파이프라인 캔버스는 만들지 않는다(설계 Z7).
- `llm` 노드 `context{var}`가 데이터 취급 문구와 함께 자료를 붙이고 인용 목록이 된다. `retriever_resources`는 `wf_run`·`wf_message`·`message`에 저장되고 `workflow.completed`·`tool_call.completed`의 선택 필드로 나간다(봉투 v2 유지).
- 에이전트는 `search_knowledge` 내장 도구(그룹 `knowledge`, 승인 등급 read)로 KB를 쓴다. 4단계 A1 레지스트리가 오면 `kind: knowledge` 항목으로 옮긴다.

### D8. 데이터 정책과 키 등급(4단계 D1·설계 Z1·Z2)
- KB·데이터 소스를 만들 때 무료 등급 약관을 보여 주고 확인을 저장한다. `key_tier: free / paid`를 두고, 유료 키(`GEMINI_PAID_API_KEY`, 새 프로젝트여야 하며 무료 목록에 섞이면 기동 거부)가 있으면 `paid` KB의 임베딩과 그 KB를 참조하는 런의 모든 모델 호출이 유료 키로 간다. 등급은 `ChatRequest.tier`로 어댑터까지 가고 자식 런은 부모와 자기 중 높은 쪽을 상속하며, 유료 키 소진 시 대기하고 무료로 떨어지지 않는다.
- 429 때 키 순환(Z2 추천안): 인제스트의 분당 429는 같은 키로 대기, 사람이 기다리는 요청은 다음 키, 일일 한도는 채팅·임베딩 모두 순환하지 않고 멈춘다. 이에 따라 ADR-0003에 "일일 한도 429는 순환하지 않는다"를, ADR-0004 D3에 폴백 기본 "3.8 → 3.6"을 한 줄씩 더한다.

### D9. 범위
- 1차 최소와 확장은 설계 3.3 표로 나눴고 사용자가 확장을 뺄 수 있다. Text2SQL 포함 여부는 설계 Z5·ADR-0008.
- 후속: LLM 생성 Q&A, 요약 인덱스, 멀티모달 임베딩(4단계 C1 뒤), 파이프라인 캔버스, 데이터소스 플러그인, Agent Knowledge Base, External Knowledge API, 워크스페이스 범위 dataset 키.

## 기각한 대안
- File Search(D1). 같은 app.db에 벡터 저장(페이지 크기·잠금·WAL). 파티션 키 한 테이블(삽입 3배 느림, 여러 KB `IN` 불가). usearch·hnswlib·DuckDB VSS·LanceDB·Chroma(메모리 상주, 의존성, 실험적 영속화). Kiwi 형태소 분석(RSS). 가중 RRF 기본값과 코사인 원값 가중합(재실측에서 min-max 가중합보다 낮음). 3072차원 기본(저장 4배에 이득 한 건). 네이티브 클라이언트를 3단계가 만드는 것(1차에 필요한 기능이 없다). 인제스트 진행 SSE(분당 몇 번 바뀌는 값). 전용 파이프라인 캔버스 1차(마일스톤 2개 분량에 1인 환경 가치가 작다). 세대 교체식 재임베딩(복잡도). 일일 한도에서의 키 순환(하루 총량이 곱절). 10분마다 재투입하는 429 재시도(일일 한도에서 하루 종일 반복).

## 영향
- 3단계 설계와 마일스톤 M21a~M29는 `docs/design/phase3-rag.md`. 1·2단계 접점은 그 문서 18장. 4단계 문서(`docs/design/phase4-options.md`)는 9·10절·D1·A3 표를 설계 3.5대로 고친다.
- 신규 의존성: 서버 `sqlite-vec`(와 Z5 (a)면 `sqlglot`). 새 데이터 파일 `data/knowledge/index.db`, 새 폴더 `data/kb-work/`, 저장소 키 `kb-files/`.
- 지금 동작이 바뀌는 것(설계 1.12): 폴백 기본값에서 3.7 제거, 캐시 단가 비율 0.10, 일일 429 비순환, 부분 색인 검색, 백업 크기, `temperature`·`top_p` 게이트.
- 설정 추가: `GEMINI_PAID_API_KEY`, `KB_EMBED_RPM`(90), `KB_EMBED_RESERVE`(10), `KB_EMBED_TPM`(0), `KB_EMBED_RPM_PAID`, `KB_EMBED_TPM_PAID`, `KB_UPLOAD_MAX_MB`(50), `KB_DOC_MAX_TEXT_MB`(8), `KB_TOP_K_MAX`(20), `KB_SEARCH_CANDIDATES`(50), `KB_EMBED_CACHE_DAYS`(30), `KB_QUERY_LOG_DAYS`(90, 0이면 끔), `KB_INDEX_CACHE_KB`, `RUNNER_MAX_CONCURRENT_INDEX_JOBS`(1).
