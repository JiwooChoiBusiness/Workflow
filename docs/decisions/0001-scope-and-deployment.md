# ADR-0001: 범위, 배포 모델, 구현 원칙, 단계 순서

- 상태: 채택 (D1, D2는 ADR-0002로 대체됨)
- 날짜: 2026-10-12
- 배경: Dify와 유사한 LLM 앱·에이전트 플랫폼을 직접 개발한다. 분석은 docs/research/dify-analysis.md 참조.

## 결정

### D1. 타깃 사용자와 테넌시
- 당분간 사내 직원이 사용한다. 단일 워크스페이스, 수십 명 규모를 가정한다.
- 멀티테넌트 SaaS는 만들지 않는다. 다만 모든 핵심 테이블에 workspace_id를 두어 나중에 확장할 여지를 남긴다.

### D2. 배포 모델
- 셀프호스팅 단일 테넌트. 사내 Linux VM 한 대 또는 사내 클라우드 VM에 docker compose로 배포한다.
- Kubernetes와 HA 구성은 사용자 수백 명 이상 또는 가용성 요구가 생길 때 검토한다. 이미지와 compose 구성은 그때 Helm으로 옮길 수 있게 유지한다.
- 개발 환경은 Windows 11 + Docker Desktop(WSL2 백엔드)이며, 운영과 동일한 compose 구성을 로컬에서 그대로 띄운다.
- 에이전트 샌드박스는 세션당 Docker 컨테이너로 격리한다. 비루트 사용자, CPU·메모리·PID 제한, 기본 seccomp, 네트워크는 egress 프록시 허용 목록 경유. gVisor 같은 강화 런타임은 운영 Linux 호스트에서 선택 사항으로 둔다.
- 인증은 초기에 로컬 계정(이메일+비밀번호, 초대제)으로 시작하고, 이후 사내 IdP와 OIDC로 연동한다.
- 소스는 GitHub에 올린다. 공개 저장소로 갈 경우 Apache 2.0을 적용한다. CI가 이미지를 빌드하고, 운영 VM에서 compose pull 후 up으로 배포한다.

### D3. 차별화 없음, 기능 복제
- Dify의 기능과 사용 흐름을 복제하는 것을 목표로 한다. 별도의 차별화 요소는 두지 않는다.
- 단, Dify 소스 코드와 화면 디자인은 1:1로 복제하지 않는다. 라이선스 추가 조건과 디자인 특허 주장 때문이다. 기능 명세와 사용 흐름만 참고해 직접 구현한다.

### D4. 의존성 원칙
- Dify 본체는 물론 graphon, dify-sandbox, dify-plugin-daemon 등 LangGenius 패키지에도 의존하지 않는다. 전부 자체 구현한다.
- LLM은 외부 API를 사용한다. 사용자가 OpenAI 호환 API와 Anthropic API 키를 제공한다. 모델 호출 계층은 프로바이더 중립으로 설계한다.
- 그 외 일반 오픈소스 라이브러리와 인프라(PostgreSQL, Redis, Docker 등)는 자유롭게 사용한다.

### D5. 단계 순서
1. 1단계: 에이전트 샌드박스. 에이전트 정의, 세션별 샌드박스 런타임, 도구(셸·파이썬·파일·HTTP), 스킬, 채팅 UI, 로그, 웹앱·API 퍼블리시.
2. 2단계: 워크플로우 엔진과 캔버스. 1단계 에이전트를 노드로 임베드할 수 있어야 한다.
3. 3단계: RAG 지식 베이스와 지식 파이프라인.
- 각 단계는 안정화 후 다음 단계로 넘어간다.

## 가정 (사용자 미확정, 설계 기본값)
- 백엔드 Python 3.12+ FastAPI, 프론트엔드 TypeScript React. Dify와 같은 계열이라 참고가 쉽고 LLM 생태계가 두텁다.
- 데이터 저장은 PostgreSQL 16, 캐시·큐는 Redis.
- 사용자가 다른 스택을 원하면 이 ADR을 갱신한다.

## 영향
- 1단계 설계는 docs/design/phase1-agent-sandbox.md에 작성한다.
- 2단계 설계 시 에이전트 노드 인터페이스(과업 입력, 선언적 출력)가 1단계 산출물과 맞아야 한다.
